# RapidMX: DNS Publishing and Admin-Console Integrations

This document is the technical design for linked features across `@rapidmx/restapi`, `@rapidmx/server`, `@rapidmx/web-client`, `postfix-bridge`, `@rapidmx/meet-plugin` and a new project, `rapidmx/dns-controller` (§7):

1. **DNS publishing.** RapidMX publishes every DNS record a deployment and its domains need, through [external-dns](https://github.com/kubernetes-sigs/external-dns), using per-domain DNS provider configurations an administrator manages in the admin console.
2. **DKIM rotation.** Each domain's DKIM key rotates on a schedule (and on demand), with the new selector published and observed live before signing switches to it.
3. **Integrations.** Third-party services an administrator chooses (DNS providers, Giphy, STUN, the S/MIME signing CA, the DNS resolver, the plugin registry) move from deployment-only configuration to typed, audited, live-applied settings in the admin console. The database is the single source of truth for all of this configuration, secrets included; a secret is stored encrypted with the deployment's configuration key (§5).
4. **Domain seeding.** The domains a deployment is installed for exist in the server from its first start, instead of being added again by hand in the admin console.

The decisions this document implements were made with JP on 2026-10-27 and are not re-litigated here (see *Resolved Decisions*). It supersedes the beta.46 stopgap that made the `openpgpkey.<domain>` host opt-in. The last proposal, the opt-in takeover of a domain's apex TXT set for SPF (§9.4), is now **DECIDED** by JP: the root TXT set is never overwritten without the admin's per-domain opt-in.

## 1. Why

The Helm chart cannot know whether a host's DNS record exists. A feature that needs a host either breaks an install or upgrade (Helm 4's `--wait` waits on cert-manager `Certificate`s, which cannot be issued for a name without a record) or ships disabled. Today that applies to `openpgpkey.<domain>` and, equally, to `mail.`, `auth.` and `autodiscover.` and to each domain's MX, SPF, DKIM and DMARC records, all of which an operator copies by hand from the admin console's DNS checklist (`GET /mail/domains/:id/dns-setup`).

Publishing those records ourselves removes the manual step, so hosts can default on, a domain added in the admin console starts receiving mail without a trip to the registrar, and DKIM keys can finally rotate.

## 2. Current Architecture

Grounding for the design below. Paths are relative to each repo.

### 2.1 What the server recommends (restapi)

`src/util/DnsSetupUtils.ts` `checkDnsSetup(dnsResolver, domain, mxHostname, autodiscoverHostname?)` computes and live-checks, per `Domain`:

| `DnsRecordType` | Kind | Name | Recommended value | Configured when |
| --- | --- | --- | --- | --- |
| `ownership` | TXT | `_rapidmx-verify.<domain>` (the apex until restapi step 3, §6.5) | `rapidmx-domain-verification=<verificationToken>` | always |
| `mx` | MX | `<domain>` | `10 <mail:dns:mx_hostname>` | `mail:dns:mx_hostname` set |
| `spf` | TXT | `<domain>` | `v=spf1 mx ~all` | always |
| `dkim` | TXT | `<dkimSelector>._domainkey.<domain>` | `v=DKIM1; k=rsa; p=<dkimPublicKey>` | selector and key set |
| `dmarc` | TXT | `_dmarc.<domain>` | `v=DMARC1; p=<dmarcPolicy ?? none>;[ rua=mailto:<dmarcReportEmail>;]` | always |
| `openpgpkey_cname` | CNAME | `openpgpkey.<domain>` | `<mail:dns:mx_hostname>` | `mx_hostname` set |
| `autodiscover_cname` | CNAME | `autodiscover.<domain>` | host of `mail:autodiscover:public_url` | autodiscover plugin active |
| `autodiscover_srv` | SRV | `_autodiscover._tcp.<domain>` | `0 0 443 <that host>` | autodiscover plugin active |

`DnsRecordCheck` is always computed fresh and never persisted. The results are checked against the public DNS through the injected `DnsResolver` (`node` or the server's `DohDnssecDnsResolver`, selected by `mail:dns:resolver`).

### 2.2 Domains (restapi)

`src/routes/BaseDomainRoute.ts` (mounted by the server at `mail/domains`) is trusted-role-only CRUD over `Domain`:

- `uid` is the normalized `name`. A rename is refused (delete and re-create).
- `verified`, `verificationToken`, `verifiedAt` and `lastCheckedAt` are server-managed (`SERVER_MANAGED_DOMAIN_FIELDS`). `verified` is never flipped back once true.
- `create()` mints a `verificationToken` and calls `ensureDkimFields()`, which asks the injected `DkimKeyProvider` for a key pair unless the caller sent both `dkimSelector` and `dkimPublicKey`.
- `POST /:id/verify` and `DomainVerificationJob` (`mail:jobs:domain_verification:schedule`, every 5 minutes) flip `verified` when the TXT record is found (`checkDomainVerification()` in `src/util/DomainVerificationUtils.ts`: any apex TXT record equal to `rapidmx-domain-verification=<token>`).
- `GET /:id/dns-setup` backfills a missing DKIM key pair, then returns `checkDnsSetup()`.
- Every create, update, delete and verification writes an `AuditLogEntry` (`DOMAIN_CREATE`/`UPDATE`/`DELETE`/`VERIFIED`).
- A pure alias domain (`aliasOf`) has its own ownership proof and DKIM key, and its own DNS records.
- The list of "this server's domains" at runtime is always the verified `Domain` rows (`DomainUtils.getVerifiedDomainNames()`, used by ingest, transport rules and the MTA's relay-domain lookup), never config.

### 2.3 DKIM keys and signing

- **Key custody (restapi, registered by the server).** `FsDkimKeyProvider` lives in restapi (`src/dkim/FsDkimKeyProvider.ts`); the server registers it (`server/src/lib/registerCoreProviders.ts`): one RSA key per domain at `<mail:dkim:key_dir>/<domain>.<mail:dkim:selector>.key` (default `/var/lib/rspamd/dkim/<domain>.mail.key`), on the `<fullname>-dkim-keys` PVC (`server/helm/templates/0_config/mail-storage.yaml`). The selector is one global value for every domain.
- **Signing (postfix-bridge).** Outbound mail is signed by **OpenDKIM inside the Postfix container** (`boky/postfix` image) of the `postfix-bridge` chart, bundled as the server chart's `postfixBridge` subchart. rspamd does not sign (its chart comment says so). The Postfix pod mounts the same PVC; its `dkim-keys-sync` init container and the `dkim-sync.sh` watcher (`postfix-bridge/helm/templates/0_config/mail-tls-policy.yaml`, run under supervisord) copy `<domain>.<DKIM_SELECTOR>.key` to `/etc/opendkim/keys/<domain>.private` every `DKIM_SYNC_INTERVAL` seconds, rebuild `KeyTable`/`SigningTable` with the one global selector, and send OpenDKIM `SIGUSR1` to reload. The mount is read-write in the Postfix container.
- **SES.** With `SesMailTransport`, SES signs with its own Easy DKIM, and `DkimKeyProvider` keys are not used.
- **No rotation.** `DkimKeyProvider.ensureKeyPair()` is documented as never rotating, and the single global selector in both the server and `dkim-sync.sh` makes a per-domain selector change impossible today.

### 2.4 Policy singletons (restapi)

`BaseMailboxPolicyRoute` (`system/mailbox-policy`) and `BaseEncryptionPolicyRoute` (`system/encryption-policy`) are the pattern Integrations follows:

- A singleton row, seeded from `@Config` values the first time it is read (`findOrSeedMailboxPolicy()`).
- The response carries `defaults`, read from config on every request, which is what the console's per-field "reset" puts a field back to. A row field that is missing (`null` on SQL) takes the config value.
- `PUT` is `@RequiresTrustedRole()` and writes an audit entry with the patch.
- Elevation (`assertAdminScope(user, trustedRoles, mail:security:elevation_max_age_seconds)`) is required for administrative actions with a larger blast radius (plugins, escrow, data export, erasure).

### 2.5 Plugin settings (restapi + server)

- A plugin's settings are saved on its `Plugin` row (`Plugin.settings`), **in plaintext**, and loaded by the server's plugin host into the first nconf layer (`PLUGIN_SETTINGS_STORE = "plugins"`), so a saved setting wins over the command line, environment and defaults.
- `CORE_CONFIG_NAMESPACES` (`src/plugins/PluginUtils.ts`, mirrored by the server's `PROTECTED_PLUGIN_SETTING_KEYS` in `src/config.defaults.ts`) lists the namespaces a plugin setting may never **declare or save**. `giphy`, `mail:dns`, `mail:pki`, `mail:domains` and `system:plugins` are on it. Reading is not restricted: the meet plugin already reads `trusted_roles` and `auth` with `@Config`.
- A secret setting (`isSecretSetting()`: key words, `secret: true` or `type: "password"` in the manifest) is masked in responses as `{ "secret": true }` (`maskSecretSettings()`), and sending the mask back means "left alone" (`isSecretMask()`; both helpers, with `secretMask()`, now live in `src/secrets/SecretMask.ts`, shared with every secret field, 5.6).
- The server's Diagnostics page hides config values named on an explicit list (`server/src/diagnostics/hiddenSettings.ts`, which already lists `giphy:api_key`, `system:plugins:registry_token` and `mail:pki:openbao:token`), never by name-guessing.

### 2.6 Kubernetes, OpenBao and configuration (server)

- The server already talks to the Kubernetes API, from `src/diagnostics/KubeClient.ts`: a small hand-written HTTPS client using the pod's service account token (re-read on every request, since bound tokens rotate), its namespace file and the cluster CA. It is GET-only and deliberately avoids `@kubernetes/client-node`.
- The chart grants it one **namespace Role** (`helm/templates/0_config/diagnostics-rbac.yaml`: `get`/`list` on `pods`, `persistentvolumeclaims` and `metrics.k8s.io` `pods`), bound to the chart's ServiceAccount, behind `global.diagnostics.rbac.create`. There is no ClusterRole, per the standing rule.
- The ServiceAccount (`0_config/service-account.yaml`) is created by default (`global.serviceAccount.create: true`; the template comment saying "off by default" is stale). The server pod mounts its token; clamav, coturn and rspamd do not.
- OpenBao, when the installer installs or uses it (`--openbao`, default true), runs in namespace `openbao` with a **plain-HTTP** listener (`http://openbao.openbao.svc:8200`) and holds the release's secrets at `<kv mount>/<fullname>/secrets`. External Secrets (`helm/templates/4_vault/external-secrets.yaml`, `SecretStore <fullname>-openbao`) syncs them into the Kubernetes Secrets the pods read. `prepareOpenbao()` enables KV v2, a PKI mount, two read-only policies and two **orphan periodic tokens** (`<fullname>-openbao-eso`, `<fullname>-openbao-pki`); **no Kubernetes auth method is enabled**, although the chart's `SecretStore` already supports `global.openbao.auth.method: kubernetes`.
- The server process does not talk to OpenBao at runtime today. restapi's `OpenBaoPkiCertificateAuthority` (static token, `mail:pki:openbao:token`) exists, but the chart never sets `mail__pki__backend`, and its `assertSafeAddress()` refuses plain HTTP to any non-loopback host, so the in-cluster address would be refused anyway.
- **Every config value is a startup snapshot.** `@Config` fields are assigned once by `ObjectFactory` at instantiation (its `config` is `protected`), and `registerCoreProviders()` picks the `DnsResolver`, CA and signing-enrollment implementations once per process. Saving a plugin setting changes `computePluginStateHash()`, which makes `PluginWatcher` roll every replica's worker under a Redis restart lock (`PluginRestartLock`).
- There is no general leader election. The reusable single-writer pieces are the Redis lock in `src/plugins/PluginWatcher.ts` and the DB lease in `src/plugins/PluginPurgeLedger.ts`.
- The server never learns its public addresses, and the installer detects none: its final message tells the operator to point A/AAAA "to this machine". The only address detection anywhere is coturn's `detect-external-ip`. The only DNS automation is `deploy/aws/bootstrap.sh`'s optional Route 53 `upsertCname()`.
- List-valued config reaches the server as a JSON string in the service ConfigMap (e.g. `cors__origins: {{ $origins | toJson | quote }}`), parsed by nconf's `.env({ separator: "__", parseValues: true })`.

### 2.7 The installer and setup (server, web-client)

`single_node_install.sh` takes `--domain`, `--mail-host`, `--auth-host`, `--mail-domains` (default `<domain>`, passed to `postfixBridge.domains`), `--openbao`, `--openpgpkey-host`, `--tls`, `--gateway`, `--install-cert-manager`, `--uninstall` and others, and installs cert-manager and External Secrets cluster-wide. Its final message tells the operator to "Add each domain in the admin console, publish the DNS records it shows". The first-run setup wizard (web-client `apps/shared/components/admin/setup/SetupWizard.tsx`, steps `plugins`, `domain`, `settings`, `escrow`, `mailboxes`, `branding`) makes the administrator add that same domain again. `BaseSetupRoute.toStatus()` reports setup `required` on a deployment that has started the wizard or has no domains.

### 2.8 `mail:domains`

Nothing reads `mail:domains` at runtime. It is on the protected-namespace lists, the doc comments of `TransportRuleUtils.buildTransportRuleContext()` and of the transport-rule `anyRecipientExternal` condition in `models/types.ts` still call the list "configured `mail:domains`" (stale: the caller passes `getVerifiedDomainNames()`; corrected in restapi step 6), and the only writer is the server's `yarn dev` helper (`src/dev/enableDevAutoLogin.ts`), which sets `["example.com"]`. This design gives the key its meaning back (§13).

## 3. Concepts

- **DNS provider config** (`DnsProvider`): a named, admin-managed configuration of one DNS hosting account: its type (`cloudflare`, `route53`, ...), non-secret options, the zones it may touch, and its credentials, encrypted (§5).
- **Assignment**: each `Domain` has `dnsProviderUid`, naming a provider config, or nothing ("manual": the admin publishes records by hand, exactly as today).
- **Desired state**: what the server says must be published: provider configs, their assignments and the desired records for each domain and for the deployment's own hosts. The server computes and stores it; it never writes to Kubernetes.
- **DNS controller**: a separate, single-replica pod with its own ServiceAccount and namespace Role, built from its own project and image (`rapidmx/dns-controller`). It reads the desired state from the server through a versioned internal API and is the only RapidMX component that creates or changes Kubernetes objects (§7).
- **Publication**: the controller writes the desired records as `DNSEndpoint` custom resources. One external-dns instance per provider config reads only the ones labelled for it and applies them at the provider.
- **Configuration secret**: a configuration value that is a credential, an API key or a token. It lives in the database row that holds the rest of its configuration, as an encrypted envelope in place of the plaintext (§5). Nothing else is encrypted.
- **Configuration keyring**: the deployment's encryption keys (`kid` -> 256-bit key), the newest of which encrypts. Delivered to the server pods only: by External Secrets from OpenBao when the deployment has OpenBao, else from a Kubernetes Secret the chart generates once (5.3). OpenBao is optional.

## 4. Data Model (restapi)

### 4.1 `DnsProvider`

New entity, Mongo and SQL, deny-all class ACL like every admin entity.

```ts
export type DnsProviderType = "cloudflare" | "route53" | "rfc2136" | "google" | "azure";

export interface DnsProvider extends BaseEntity {
    /** Server-generated, stable, DNS-label-safe (lowercase letters, digits, hyphens; at most 40 characters). It names the
     * external-dns Deployment, its Secret and its label value, so it never changes. */
    uid: string;
    /** Display name, unique (case-insensitive). */
    name: string;
    /** `name` in lowercase, under a unique index on both backends, so two writes racing past the name check can't both save the same
     * name (the loser gets the same 409). Server-set, never returned. */
    nameKey: string;
    type: DnsProviderType;
    /** The zones (apex names) this config may publish into: external-dns's --domain-filter. At least one. A Domain may be
     * assigned to this config only when its name is one of these or under one of them. */
    zones: string[];
    /** Non-secret, type-specific options, validated per type (4.2), with every default filled in. A value is text, a number, a switch or a
     * list of text (Cloudflare's `zoneIds`, rfc2136's `hosts`). */
    options: Record<string, string | number | boolean | string[]>;
    /** The credentials, one encrypted envelope per secret field of the type (4.2), keyed by the field name (5.2; associated data
     * `DnsProvider`, `uid`, `credentials.<field>`). Unset until credentials are saved (and for a config that needs none: Route 53
     * through IRSA, unsigned rfc2136); `null` once every credential was cleared. Never returned (10.1 shows masks). */
    credentials?: Record<string, ConfigEnvelope> | null;
    /** Bumped on every change to `credentials`: the controller rewrites the external-dns Secret when it differs (7.4), and the
     * Deployment's pod-template annotation carries it, so new credentials roll the pod. 0 before any. */
    credentialsGeneration?: number;
    /** Set by the installer for the config it created, so the console can say where it came from. */
    origin?: "installer" | "console";
    /** Admin on/off. A disabled config's external-dns instance is scaled to zero; its records stay as they are. */
    enabled: boolean;
    /** Allow the takeover of records this deployment does not own yet in these zones (9). Default false. */
    allowTakeover: boolean;
    /** Written only from the controller's status reports (7.7). Never client-settable. */
    status?: DnsProviderStatus | null;
}

/** What the controller last reported (7.7); every field optional, since a config the controller hasn't reported on has none. */
export interface DnsProviderStatus {
    reportedAt?: Date;
    readyReplicas?: number;
    image?: string;
    lastRolloutAt?: Date;
    lastSyncAt?: Date;
    registryErrors?: number;
    sourceErrors?: number;
    providerErrors?: number;
    ownerMismatchRecords?: number;
    lastError?: string;
}

```

`ConfigEnvelope` is the encrypted form of one secret value (5.2). First built (restapi step 2) with `secretRef?: SecretRef | null`, a reference to the credentials in a separate secret store; replaced by `credentials` and `credentialsGeneration` in restapi R2 (18), as above. `credentialsGeneration` is 0 on a row that never had credentials (a SQL column with that default); `credentials` is left unset on such a row and set to `null` once every credential was cleared.

### 4.2 Provider types

Each type declares its options and its secret fields. Option values are validated (types, enumerations, host names); unknown keys are refused. All values become external-dns arguments or environment variables (7.4); none is interpolated into a shell or a file path.

| Type | Options (non-secret) | Secret fields | external-dns provider | Tested |
| --- | --- | --- | --- | --- |
| `cloudflare` | `zoneIds` (required: one per zone, passed as `--zone-id-filter`, which is what lets a token scoped to one zone work). Proxying is never offered: mail hosts must not be proxied, and external-dns forces MX/TXT/SRV unproxied anyway. | `apiToken` (required) | `cloudflare`, env `CF_API_TOKEN` | e2e (powerlevel.gg) |
| `route53` | `region`, `zoneType` (`public`/`private`, default public), `assumeRoleArn`? | `accessKeyId`, `secretAccessKey` (both or neither: neither means IRSA on the external-dns ServiceAccount) | `aws`, env `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`/`AWS_REGION` | unit only |
| `rfc2136` | `hosts`, `port` (53), `zone`, `tsigKeyName`, `tsigAlgorithm` (`hmac-sha256` ...), `insecure` (bool, default false); `--rfc2136-axfr` always on (sync needs it) | `tsigSecret` (base64, required unless `insecure`) | `rfc2136`, env `EXTERNAL_DNS_RFC2136_TSIG_SECRET` (every flag has an `EXTERNAL_DNS_<FLAG>` variable) | unit + CI (bind9) |
| `google` | `project` | `serviceAccountJson` | `google`, mounted file + `GOOGLE_APPLICATION_CREDENTIALS` | unit only |
| `azure` | `tenantId`, `subscriptionId`, `resourceGroup` | `clientId`, `clientSecret` | `azure`, `azure.json` (`aadClientId`/`aadClientSecret`) mounted from the Secret, `--azure-config-file` | unit only |

Providers that are not live-tested carry `tested: false` in `GET /types`, and the console marks them "not yet live-tested".

The registry is `src/dns/DnsProviderTypes.ts` (restapi). Beyond the table, as implemented: Cloudflare's `zoneIds` are 32-character hex ids, one per zone **in the order of `zones`**, never repeated; rfc2136's `zone` must be one of `zones`, `tsigKeyName` is required unless `insecure`, and `tsigAlgorithm` is one of `hmac-sha1`/`-sha224`/`-sha256` (default)/`-sha384`/`-sha512`; Route 53's `region` and `assumeRoleArn`, Google's `project` and Azure's GUIDs and resource group are checked for shape. Credential values are checked for shape too (an AWS access key id, a base64 TSIG secret, a JSON object for Google's key file, a GUID client id), with errors that name the field and never repeat the value.

Facts checked against external-dns v0.23.0's source and docs (2026-10-26):

- **DigitalOcean is not offered**: its in-tree provider was removed in v0.21.0 and is only reachable through a third-party webhook provider. DigitalOcean and webhook providers come later.
- **Record kinds per provider.** MX is supported by cloudflare, aws, google and azure. **rfc2136 cannot manage MX or SRV**: it writes them but its AXFR reader skips them, so they can never be updated or deleted. For an rfc2136 config the controller publishes A/AAAA/CNAME/TXT only, and the MX and SRV records show as **manual** (with the reason) for the admin to keep by hand; so do most of its TXT values (below).
- MX targets are `"<preference> <host>"`; SRV targets must end with `.`; A/AAAA targets must not end with `.`.
- **TXT targets are written quoted** in a `DNSEndpoint` (`"\"v=spf1 mx ~all\""`, i.e. the target string itself begins and ends with `"`), the same form the TXT registry writes its own ownership records in. Proven on Cloudflare by the takeover spike (2026-10-27, §9.3). **Route 53 settled from v0.23.0's source (2026-10-28):** external-dns sends a TXT target to Route 53 exactly as given and reads it back unchanged, so the quoted target equals what it reads and a sync changes nothing; targets are compared without regard to case (`Targets.Same` uses `strings.EqualFold`). Route 53 keeps its "not yet live-tested" badge only for AWS's own validation, and is covered by unit tests against recorded API fixtures. **A value over 255 bytes must be pre-split** into quoted chunks (below), checked live on Cloudflare (2026-10-28): an unsplit long value is split by Cloudflare itself, so what external-dns reads back never equals the target and the record is planned for update on every sync, while a pre-split value is stable. One helper (`quoteTxtTarget()`, in the controller) does it, and the golden manifests test it. As implemented (dns-controller C3), a value longer than one 255-byte character-string (a 2048-bit DKIM key, about 410 characters) is written as several, `"\"<first 255 bytes>\" \"<rest>\""`, the zone-file form Route 53 requires and the split form Cloudflare stores long values in; a cut never splits a UTF-8 character, and `"` and `\` inside a value are escaped after cutting. The split form is stable on Cloudflare (checked live 2026-10-28, above), and the e2e's DKIM rotation checks it again with a real 2048-bit key. **The quoted form is for Cloudflare, Route 53 and Google only** (`txtTargets()`, checked in v0.23.0's providers after review): Azure writes and reads its first target verbatim (`provider/azure/azure.go`), so quotes would be published as part of the value, and rfc2136 reads back bare character-strings (next bullet). Azure gets the value unquoted and unsplit (whether Azure's API takes one string over 255 bytes is part of its "not yet live-tested").
- **TXT values a provider can't keep** are left out of the endpoint, like rfc2136's MX and SRV, and show as **manual** (`kind_unsupported`; as implemented in restapi R2, `dnsManualReason()` takes the record's values and judges a whole TXT record by them, the same rule as the controller's `txtTargets()`: one value that fails it makes the record manual). The reason comes in the order of 4.4, so on rfc2136 an SPF record that isn't managed reads `kind_unsupported` rather than `apex_txt_unmanaged`: opting in wouldn't make rfc2136 keep it.
  - **Azure, a TXT name with several values** (a managed apex set with kept values): external-dns v0.23.0 writes and reads only `Targets[0]`, so the other values would be lost and the set rewritten every interval. **As implemented (restapi R2)**, `PUT mail/domains/:id/apex-txt` is answered 400 for an Azure config with a non-empty `keep`, on the opt-in and on editing the kept values later, and an opt-in with none is allowed (SPF alone is one value); opting out is never refused. **Also refused (400) for rfc2136**, whose SPF value (it has spaces) can never be one plain character-string, so the set could never be published or owned (`providerKeepsTxt()`, the rule `dnsManualReason()` applies).
  - **rfc2136, any value that isn't one plain character-string** (a space, `;`, `"`, `\`, `(`, `)`, `$`, `@`, non-ASCII, or over 255 bytes; so SPF, DKIM and DMARC, but not the ownership-verification TXT): its `Records()` returns the bare strings, which never equal a quoted target, and `RemoveRecord` re-parses what it read as zone-file text, where `;` starts a comment and a space separates strings, so an old value is never removed: a changed DMARC policy would leave two DMARC records, a deleted domain its SPF and DKIM. Plain values are written unquoted, which reads back equal.
- **Cloudflare tokens with a client-IP restriction** must list every address the cluster egresses from, IPv4 **and** IPv6: the spike's token was restricted to the node's IPv4 address and its calls failed whenever the pod went out over IPv6. The console's Cloudflare form and the installer's documentation say so.

### 4.3 `Domain` additions

| Field | Meaning |
| --- | --- |
| `dnsProviderUid?: string \| null` | The provider config publishing this domain's records; unset or `null` means manual. Set only through `PUT /:id/dns-provider` (10.4). Must name an existing `DnsProvider` whose `zones` cover the domain. |
| `origin?: "seed" \| "console" \| null` | `"seed"` for a domain the server created from `mail:domains` (13), `"console"` for one added through `POST mail/domains` (as implemented in restapi step 6; a client can't choose it). Unset on existing rows, which count as console-created. Server-managed. |
| `dnsPublication?: DnsPublicationStatus` | Written from the controller's status reports and the live check, see 4.4. Server-managed. |
| `dkimRotation?: DkimRotationState` | Rotation state, see 6.2. Server-managed. |
| `dkimManaged?: boolean \| null` | `true` when the current key came from the `DkimKeyProvider` (rotation possible), `false` when an admin imported `dkimSelector`/`dkimPublicKey` by hand (never rotated automatically). Set on create (`false` when the caller sent both fields), on a DKIM backfill (`true`) and on a `PUT` that changes either field (`false`). Unset on rows from before restapi step 4 until the rotation job or a rotate request asks the provider whether it holds that key (`findKeyPair()`, 6.2) and records the answer. Server-managed. |
| `apexTxt?: { managed: boolean; keep: string[]; spf?: string } \| null` | **DECIDED (§9.4).** Whether RapidMX owns the domain's apex TXT set to publish SPF, the foreign values it keeps in that set, and the SPF value it publishes there (chosen at opt-in). Set only through `PUT /:id/apex-txt` (trusted role and elevation, audited). Unset means not managed. `keep` stays on the row after opting out, so the console can show what was restored. |

All of them join `SERVER_MANAGED_DOMAIN_FIELDS`, each with the restapi step that adds it (`dnsProviderUid` and `dnsPublication` in step 2; `apexTxt` and `dkimRotation` in step 3, which reads the rotation's `next`/`previous` selectors for the `dkim_next`/`dkim_previous` records; step 4 writes it and adds `dkimManaged`; `origin` in step 6). As the code already treats `verified` and the other server-managed fields: a plain `PUT` **drops** them (so a console round-tripping a domain still works), `PUT /:id/:property` **refuses** them (403), and a create never takes them.

### 4.4 Publication status

```ts
export interface DnsPublicationStatus {
    /** The DNSEndpoint resources the controller last applied for this domain, and what external-dns has observed. */
    endpoints: { name: string; generation: number; observedGeneration?: number }[];
    /** Per record (same identity as DnsRecordCheck: type + recordName). */
    records: DnsRecordPublication[];
    lastReconciledAt?: Date;
    lastError?: string;
}

export interface DnsRecordPublication {
    type: DnsRecordType | "host_a" | "host_aaaa" | "host_cname";
    recordName: string;
    recordKind: "A" | "AAAA" | "CNAME" | "MX" | "TXT" | "SRV";
    /** "published": external-dns observed it and the live lookup sees it (7.5); "pending": applied, not yet live;
     * "conflict": a record at this name exists that this deployment does not own (9); "manual": the admin publishes it,
     * with `manualReason`. */
    state: "published" | "pending" | "conflict" | "manual";
    manualReason?: "no_provider" | "kind_unsupported" | "outside_zones" | "apex_txt_unmanaged";
}
```

`DnsRecordCheck` gains an optional `publication?: DnsRecordPublication["state"]` (and `manualReason`), so `GET /:id/dns-setup` keeps its shape and the console can show "Automatic: published / pending / conflict" or "Manual" next to the live check. The live check (`found`/`matches`) stays the source of truth for "is it working". As implemented (restapi step 3), `checkDnsSetup()` computes the state when asked (`options.publication`; the route always asks) and only for a configured record:

- **manual**, with the first reason that applies, in this order: `no_provider` (none assigned, or the one assigned is gone), `outside_zones`, `kind_unsupported`, `apex_txt_unmanaged` (`dnsManualReason()`).
- **conflict**: a live record is there and external-dns's registry record for it (`rmx-<kind>.<name>`) does not name this deployment's owner id (`rapidmx-<installationId>`), whether or not the value matches. Not reported while the owner id can't be read.
- **published**: the live check matches, the live values at the name are **exactly** the desired ones (each once, in any order; host names without case or the final dot), and external-dns has observed the domain's endpoint (`observedGeneration >= generation` in `dnsPublication.endpoints`, from the status reports). The exact comparison matters because the live check's own `matches` is looser ("is it working": any DMARC record, an SPF with `mx`, a DKIM record carrying the key) and the observed generation can be the one from before the latest change: a stricter DMARC policy, or a value added to a managed apex set, stays pending until it is live.
- **pending**: anything else.

The `ownership` check also carries `legacyApex: true` while the token is (still) at the domain's root (§6.5).

### 4.5 `IntegrationSettings`

One singleton row (`uid: "integrations"`, `INTEGRATION_SETTINGS_UID`), Mongo and SQL (one JSON column per section on SQL), deny-all class ACL:

```ts
export interface IntegrationSettings extends BaseEntity {
    giphy?: { enabled?: boolean; apiKey?: ConfigEnvelope } | null;
    stun?: { urls?: string[] } | null;
    signingCa?: { backend?: "rfc8823" | "manual" | "none"; directoryUrl?: string; contactEmail?: string } | null;
    dnsResolver?: { mode?: "node" | "doh-dnssec"; dohEndpoint?: string } | null;
    pluginRegistry?: { url?: string; token?: ConfigEnvelope; namespaces?: IntegrationPluginNamespace[] } | null;
}

/** A `PluginNamespace` as stored: its npm token, when it has one, encrypted. */
export interface IntegrationPluginNamespace { name: string; registry?: string; token?: ConfigEnvelope }
```

A field left unset means "use the deployment's configured value"; reset deletes the field (a section with nothing left is `null`). DNS providers are their own entity, but the console groups them under Integrations.

As implemented (restapi step 5):

- **Not seeded from config**, unlike `MailboxPolicy` (first drafted as "seeded from config like `MailboxPolicy`"): the row is created empty by the first change. Copying config into it would report the deployment's values as the administrator's (`source: "admin"`, 10.2) and stop a later change of the deployment's config from applying, against "unset means the deployment's value".
- **Secrets encrypted in the row** (decided 2026-10-28, §5; rework R3 of restapi step 5): the Giphy key (`giphy.apiKey`), the registry token (`pluginRegistry.token`) and each namespace's npm token (`pluginRegistry.namespaces[].token`) are envelopes, with the associated data `IntegrationSettings`, `integrations` and the field (`giphy.apiKey`, `pluginRegistry.token`, `pluginRegistry.namespaces.<scope>.token`), so a token copied to another namespace doesn't decrypt. One row write saves the secrets with the rest of the section: there is no second store, so a failed write changes nothing and needs no cleanup.
- **As first built** (restapi step 5, `9013465`), the row held `apiKeyRef`, `tokenRef` and `namespaceTokensRef` (`SecretRef`s into a `SecretStore` under `server/`, a new path per write, the namespaces' tokens in one secret keyed `ns-<scope in hex>`). The rework (**decided by JP, 2026-10-28**) renames the fields to the ones above (no release ever stored a reference: restapi with step 5 is unreleased, and the server registers only `NullSecretStore`, which refused every secret write) and deletes the path per write, the store writes and their cleanup.

### 4.6 Installation identity

A singleton row `DeploymentIdentity { installationId }`: a random 16-character value created once, the stable part of the external-dns owner id (7.4). It never changes for the life of the database.

### 4.8 Operations and the controller's state

Two models arrive with the desired-state API (restapi step 3), Mongo and SQL, deny-all class ACL:

- **`DnsOperation`**: a one-shot operation the controller runs (`type`: `test`, `takeover` or `restore`), with `providerUid`, the `domainUid` and `endpointSetId` it concerns, the `records` it writes (TXT values unquoted), `state` (`queued`, `running`, `succeeded`, `failed`), the controller's `message`, `requestedBy`, `startedAt` and `finishedAt`. Queued by `POST system/dns-providers/:id/test` and `/:id/takeover`, by an apex TXT opt-in (takeover) and by an opt-out or the deletion of a managed domain (restore). Handed to the controller in the desired state while `queued` or `running`; a finished one is never reopened by a later report. An operation that can no longer run is marked `failed` with a message starting `Cancelled:`: a restore queued for an opt-out or a domain deletion whose own write then failed, and the queued or running operations of a provider config that is deleted (10.1).
- **`DnsControllerState`**: a singleton (`uid: "dns-controller"`) holding the controller's last `handshake` (its versions, `compatible`, `selected`, `reason`, when), the Lease holder's `lastReport` (its version, the desired-state version, the Lease holder and identity, when) and `lastStandbyReport`, the same of the last report from a pod that didn't hold the Lease (7.3), which `GET system/dns-providers/controller` serves to the console.

### 4.9 `ConfigKeyState`

A singleton (`uid: "config-keys"`, restapi with the configuration encryption), Mongo and SQL, deny-all class ACL, holding the rotation's progress for the server copies and the console (5.5), never key material:

- `activeKid?: string`: the key new values are encrypted with, set when a new key is activated (5.5). Unset on a deployment that has never activated a key, where the oldest key in the ring (the original, the only one outside a first rotation) encrypts, so the key a first rotation adds never encrypts before it is activated (5.3).
- `rotation?: { kid?: string; previousKids: string[]; compromised: boolean; requestedBy: string; requestedAt: Date; phase: "adding" | "activating" | "reencrypting" | "retiring" | "done" | "failed"; activationStartedAt?: Date; waitingFor?: string[]; activatedAt?: Date; activationForced?: { by: string; at: Date; staleCopies: string[] }; finishedAt?: Date; lastError?: string } | null`: the current or last rotation. `kid` is the new key once it is in the keyring; `previousKids` the keys it replaces; `waitingFor` the server copies (pod name and process id) that haven't yet reported loading the new key while `phase` is `activating`, and, once activated, those that don't yet encrypt with it; `activationForced` is set by "Activate anyway" (5.5) with the copies that hadn't loaded the key then; `lastError` names what failed (a keyring write refused, for example), never a value.
- `kidUsage?: Record<string, number>` and `countedAt?: Date`: the envelopes per `kid` at the end of the last full re-encryption pass.
- `reencryption?: { targetKid: string; complete: boolean; startedAt: Date; finishedAt?: Date; unreadable?: { record: string; uid: string; field: string; kid: string }[] }`: `complete` is whether the last pass saw every row and saved every change (a row changed meanwhile makes it `false`); `unreadable` names, at most 50, the envelopes the pass couldn't decrypt (never a value), which the console lists (5.5, step 3).
- `pluginSecrets?: { encryptedAt?: Date; waitingForRollout?: boolean; checkedAt?: Date; reason?: string }`: the plugin secret settings' encryption (5.7). `encryptedAt` is the first completed run of `PluginSecretEncryptor`; until it is set, secret settings are saved in plaintext and the encryptor waits for the server's rollout, `reason` saying why it is still waiting (old pods, or the pods can't be listed).

## 5. Configuration Secrets

**Decided by JP (2026-10-28)**, replacing the first design ("secrets live in OpenBao or Kubernetes Secrets, never in the database"), which gave configuration two stores and was built in restapi steps 1, 2, 5 and 7 and in dns-controller C3; 18 lists what is reworked. JP's requirements:

- The **database is the single source of truth for all configuration**, secrets included. Every setting stays editable at runtime in the admin console.
- Secrets are **encrypted at rest**: a database dump or backup alone reveals none.
- The encryption key is **fed by OpenBao** when OpenBao is installed, and **OpenBao is optional**: everything works without it.

### 5.1 What is a secret, and where it lives

**Decided (2026-10-28):** a configuration secret is a credential, an API key or a token, and nothing else:

| Secret | Row and field |
| --- | --- |
| DNS provider credentials (4.2's secret fields) | `DnsProvider.credentials.<field>` (4.1) |
| Giphy API key | `IntegrationSettings.giphy.apiKey` (4.5) |
| Plugin registry token | `IntegrationSettings.pluginRegistry.token` |
| A plugin namespace's npm token | `IntegrationSettings.pluginRegistry.namespaces[].token` |
| A plugin setting `isSecretSetting()` classifies as secret (plugins mark only credentials) | `Plugin.settings.<key>` (5.7) |

Each is stored as an encrypted envelope (5.2) in the field where it would otherwise be plaintext, in the row that already holds the rest of its configuration; a future row with a secret does the same. Every other value stays plaintext, so it remains queryable and readable in Diagnostics. Deployment configuration from Helm and the environment (the JWT secret, the ingest secret, S3 keys, ...) is not part of this and stays where it is.

### 5.2 Encryption: `ConfigCipher` (restapi)

- **Algorithm:** AES-256-GCM through `node:crypto`, a random 96-bit nonce per value, a 128-bit tag. No new dependency.
- **Envelope**, stored in place of the value:

```ts
export interface ConfigEnvelope {
    $enc: 1;      // format version; isConfigEnvelope() checks for exactly these five keys
    kid: string;  // the keyring entry that encrypted it (5.3)
    iv: string;   // base64, 12 bytes
    ct: string;   // base64 ciphertext of the UTF-8 JSON of the value, so a plugin's number or flag comes back as one
    tag: string;  // base64, 16 bytes
}
```

- **Associated data** binds a ciphertext to where it belongs: the format tag `rapidmx-config/1`, the record type (`DnsProvider`, `IntegrationSettings`, `Plugin`), the row's `uid` and the field path (`credentials.apiToken`, `giphy.apiKey`, `pluginRegistry.namespaces.<scope>.token`, `settings.<key>`), each part length-prefixed so no two contexts encode alike. An envelope copied into another row or field fails to decrypt, so write access to the database alone can't make the server hand one secret out as another (a DNS credential as a plugin setting, say).
- **`ConfigCipher`** (restapi `src/secrets/ConfigCipher.ts`, DI token `"ConfigCipher"`): `encrypt(value, context)`, `decrypt(envelope, context)`, `isEnvelope(value)`, `currentKid()`. It encrypts with the active key (5.3) and decrypts with whichever key the envelope's `kid` names. A failure (a `kid` not in the ring, another context, a changed byte) is a `ConfigSecretUnavailableError` naming the record and field, never the value; the consumer treats the secret as unset (5.4).
- **A key is required in production.** The server refuses to start without a usable keyring when it runs in production, the rule it already applies to the JWT secret. In development (`yarn dev`) it generates a keyring into a local, git-ignored file on first start. restapi's tests use a fixed test keyring.
- It replaced restapi step 1's `SecretStore` interface, `NullSecretStore` and `SecretRef`, which restapi R4 removed (18.2). The masks (`src/secrets/SecretMask.ts`) and `HostConfig` stay as built.
- **As implemented (restapi R1a).**
  - **Files:** `ConfigEnvelope` and `ConfigKeyState` are in `models/types.ts`; the keyring document (`parseConfigKeyring()`, `readConfigKeyring()`, `generateConfigKey()`, `serializeConfigKeyring()`, `CONFIG_KEY_STATE_UID`) and the guard and development helpers are in `src/secrets/ConfigKeyring.ts`; the cipher is in `src/secrets/ConfigCipher.ts`.
  - **The registered classes are `ConfigCipherMongo` and `ConfigCipherSQL`** (`util/mongo`, `util/sql`, like `DomainSeederMongo`/`SQL`), which register under the DI token `"ConfigCipher"` and read `ConfigKeyState.activeKid` from their datastore; the base `ConfigCipher` has no datastore and uses the oldest key.
  - **API:** `encrypt(value, { record, uid, field })`, `decrypt(envelope, context)` (the sealed text, number or flag) and `decryptString(envelope, context)` (a credential or key: a number or flag is `invalid`, never returned as text) are synchronous, since a decryption that meets an unknown `kid` re-reads the keyring file on the spot; `reload()` is asynchronous (it also reads the active kid) and never throws, which is what the rotation notice calls. A value is a text, a finite number or a flag (`ConfigSecretValue`).
  - **Reloads:** the periodic reload skips a tick while the previous one still waits on the datastore, and a read of `ConfigKeyState` that finishes after a later one started is discarded, so a slow old answer never replaces a newer `activeKid`.
  - **Failures:** `ConfigSecretUnavailableError` carries `record`, `uid`, `field` and a `reason` (`unknown_key`, `invalid` or `failed`), and its message names the record and field, never a value, an envelope or a key. With no keyring loaded, `encrypt()` answers 503. A reload that fails (an unreadable or malformed file, the key state row unreadable) keeps what the process has and logs once per distinct failure; failing to read the keyring at startup is logged as an error. No error message repeats the keyring's text (V8's `JSON.parse` message quotes it).
  - **The keyring** takes `config_encryption:keyring_file` over `config_encryption:keyring` when both are set; a `kid` is 1 to 64 letters, digits, `-` or `_` (a rotation makes 8 hex digits); each key is exactly 32 bytes in base64 with an ISO 8601 `createdAt`; of two keys created at the same moment the later in the list is newest.
  - **Guard and development helpers:** `assertProductionConfigKeyring(source, production = NODE_ENV === "production")` throws in production without a usable keyring and checks nothing otherwise; `ensureDevelopmentConfigKeyring(file)` creates the file (mode 0600, race-safe) with one new key on first use and never overwrites a file that isn't a keyring. The server decides the development file's path and git-ignores it.
  - **`maskCredentials(credentials)`** takes the row's `credentials` (or any record): each field that holds a value is shown as the mask. `BaseDnsProviderRoute` passes it the row's `credentials` since R2.

### 5.3 The keyring and its delivery

- **One keyring per deployment**, the "configuration keyring": a JSON document `{ "keys": [ { "kid": "<8 random hex>", "key": "<base64 of 32 random bytes>", "createdAt": "<ISO 8601>" } ] }`, usually one entry, two or more only during a rotation (5.5). The **active** key encrypts: `ConfigKeyState.activeKid` (4.9) when it is set and in the ring, else, when no key has ever been activated, the oldest by `createdAt` (the original key, which every copy has; a first rotation's newly added key therefore never encrypts before it is activated), and, when `activeKid` names a key this copy hasn't loaded yet, the newest it has. Every entry decrypts. Only the server pods receive it.
- **Activation** (**decided by JP, 2026-10-28**): a key added by a rotation encrypts only once every running server copy has reported loading it (5.5), so no copy writes a value another can't yet decrypt (a mounted Secret reaches each node's kubelet at its own time, and External Secrets adds its refresh interval). Until then the previous key still encrypts, so a stalled activation breaks nothing. It never activates on a timeout; an admin who knows a stale copy is being replaced can "Activate anyway" (elevated, audited, 5.5). This replaces the first draft's fixed delay (a new key encrypting once 10 minutes old, `config_encryption:activation_delay_minutes`), which guessed at propagation instead of observing it.
- **Server config** (`config_encryption`, a new namespace on restapi's `CORE_CONFIG_NAMESPACES` and the server's `PROTECTED_PLUGIN_SETTING_KEYS`): `config_encryption:keyring_file` (the chart sets `/etc/rapidmx/config-keyring/keyring.json`) or `config_encryption:keyring` (the JSON itself, for development and tests; hidden from Diagnostics). **Decided by JP (2026-10-28):** the file is re-read every minute, at once when a rotation notice arrives (5.5), and at once (at most once a minute) when an envelope names a `kid` the process doesn't have, so a rotation reaches every process without a restart (the approved plan's section 4 said "loaded once at startup"; its rotation amendment needs it reloaded). Where the server writes a new ring (**approved 2026-10-28**) is `config_encryption:keyring_store:backend` (`kubernetes`, `openbao`, `file` or `none`; the chart sets the first or second, `yarn dev` the third) with `config_encryption:keyring_store:secret_name` (`<fullname>-config-keyring`) or `config_encryption:keyring_store:kv_mount` and `kv_path` (`<fullname>/config-keyring`); with `none` (a keyring given inline) rotation is refused with 503.
- **Without OpenBao:** the chart generates the keyring (one entry, `randBytes 32`) into the Secret `<fullname>-config-keyring`, key `keyring.json`, on first install, the way it already generates the JWT, coturn and rspamd secrets and keeps them across upgrades through `lookup`. **Decided by JP (2026-10-28):** unlike those, which are re-rendered from `lookup` on every upgrade, this one is rendered only while `lookup` finds none, with `helm.sh/resource-policy: keep`, and left to the server's rotation afterwards (5.5): an upgrade re-rendering it from a `lookup` made just before a rotation added a key would write the older ring back, and every value encrypted with the new key would be lost. An uninstall therefore leaves it in place (the installer's uninstall says so, 12.4).
- **With OpenBao** (`global.openbao.enabled`; **decided 2026-10-28: a KV secret delivered by External Secrets**, not the Transit engine, which would make OpenBao a hard dependency of server startup): the keyring is the KV secret `<kv mount>/<fullname>/config-keyring` (property `keyring`), a path of its own rather than a key under `<fullname>/secrets`, so the server's write access can be limited to it (5.5, 5.8; the approved plan's section 5 said "one more secret in the release's existing OpenBao path", its rotation amendment "a policy that can write only that KV path"). The chart renders an `ExternalSecret` `<fullname>-config-keyring` (the release's `SecretStore`, `creationPolicy: Owner`) that materializes the same Secret, instead of generating it, with a short `refreshInterval` (`1m`, `configEncryption.externalSecretRefreshInterval`; **decided by JP, 2026-10-28**) so a key the server adds reaches the pods quickly. The installer creates the KV entry once. When an existing deployment moves to OpenBao, the installer first copies the Secret's keyring into OpenBao, so nothing needs re-encrypting, then deletes the kept Secret for External Secrets to own. OpenBao sealed or unreachable leaves the Secret as last synced.
- **Only the server pods** mount the Secret (read-only; the kubelet mounts it). The server writes a new ring only through the Kubernetes API (without OpenBao: `get` and `update` on that one Secret by `resourceNames`) or OpenBao (with OpenBao: that one KV path), never through the mount (5.5).

### 5.4 Decrypted values in memory

**Decided by JP (2026-10-28):** each server process decrypts a secret the first time it needs it and keeps the plaintext in memory for the life of the process; there is no per-request database read or decryption. A compromised server process already holds the key, so decrypting at every use would cost performance without stopping a real attack (JP's standing rule: a security measure must address a real threat). Plaintext is still never written to the database, a log line, an audit entry, an error or an API response.

The caches are the places that already hold configuration, invalidated by the change notices that already exist or are designed:

| Secret | Held in | Dropped and reloaded on |
| --- | --- | --- |
| Giphy key, registry and namespace tokens | the server's `integrations` config layer (11.1), read through `HostConfig` | `rapidmx:integrations:changed` on Redis (11.2, server step 6), and the row-version timer that catches a missed notice |
| Plugin secret settings | the `plugins` config layer the plugin host builds at worker start (5.7) | the plugin change message (`PLUGIN_EVENTS_CHANNEL`), which rolls the workers as any settings change does |
| DNS provider credentials | not kept: decrypted only to answer the controller's credentials request (7.3), which comes only when a config's `credentialsGeneration` moves or its Secret is missing | (nothing to drop) |

A value that can't be decrypted (a `kid` missing from the keyring, for example after restoring a database with an older keyring, 5.9) is left out, so the deployment's value or the plugin's default applies; the server logs it once per record and field (never the value), and Diagnostics and the console show the field as "set, but can't be read: enter it again".

### 5.5 Key rotation

**Decided by JP (2026-10-28): manual only, performed inside the server.** This replaces the first 2026-10-28 design (an automatic rotation every 182 days, `rotation_days`, by a key-rotator `CronJob` running the dedicated `rapidmx/config-key-rotator` image, with its own Role or OpenBao policy, an internal API `/internal/config-keys/v1/*` with shared contract fixtures, and a console "run now"), all of which is dropped: there is no schedule, no CronJob, no rotator project or image and no internal API for it.

- **New values always use the active key; any key in the ring decrypts** (5.3).
- **Started by an admin only:** "Rotate configuration key" in the console (`POST system/config-keys/rotate` with `{ compromised?: boolean }`, 10.5; trusted role and elevation, audited `CONFIG_KEY_ROTATION_REQUESTED`), for a routine rotation or for a suspected compromise of the keyring. Nothing rotates on its own.
- **The server's write rights** (**approved by JP, 2026-10-28**), limited to the keyring and nothing else:
  - **Without OpenBao:** the chart adds a Role `<fullname>-config-keyring` whose only rule is `get` and `update` on `secrets` with `resourceNames: [<fullname>-config-keyring]`, bound to the server's ServiceAccount. `KubeClient` (2.6), GET-only today, gains one write: a `PUT` of that Secret with its `resourceVersion`, so a concurrent change fails the write rather than being overwritten (the server reads again and retries).
  - **With OpenBao:** no Kubernetes write right at all. The server's OpenBao role `<fullname>-server` (5.8) gains `read` and `update` on `kv/data/<fullname>/config-keyring` and `read` on its metadata (it must read the ring to add to it), through the existing `OpenBaoClient` and its Kubernetes-auth login, writing with KV v2's check-and-set. External Secrets syncs the KV secret into `<fullname>-config-keyring` (`refreshInterval: 1m`, 5.3), which the pods mount.
  - The server stays **read-only on every other Kubernetes resource** (7.6, §15).
- **The steps**, run by `ConfigKeyRotationJob` (restapi, Mongo and SQL, registered by the server with its other jobs; `config_encryption:rotation:schedule`, default every 30 s while a rotation is in progress or re-encryption has work, and at once on the rotation notice `rapidmx:config-keys:changed` on Redis; approved 2026-10-28), on every replica under a Redis lock so one copy acts at a time, each step recorded on `ConfigKeyState.rotation.phase` (4.9) so another copy can take over after a restart:
  1. **`adding`.** The server generates the key (32 bytes and an 8-hex `kid` from `node:crypto`'s `randomBytes`), reads the ring with its version (the Secret's `resourceVersion` or the KV version), adds the entry and writes it back with that version (`ConfigKeyringStore`: a restapi interface, implemented in the server by `KubernetesConfigKeyringStore` and `OpenBaoConfigKeyringStore`, and by `FileConfigKeyringStore` for `yarn dev`). Audited `CONFIG_KEY_ROTATED`. A refused write (a conflict, OpenBao sealed, a missing right) is retried on the next run and shown as `lastError`; the ring is unchanged.
  2. **`activating`** (**decided by JP, 2026-10-28**). The new `kid` encrypts only once **every running server copy has loaded it**. Each server process (each worker of each pod) keeps a heartbeat in Redis, `rapidmx:config-keys:loaded:<pod name>:<pid>` with a TTL of three heartbeats (`config_encryption:activation:heartbeat_seconds`, 30 s, so 90 s), holding the `kid`s in its ring and the one it encrypts with, refreshed on every heartbeat and at once after each keyring reload. Activation waits until every live heartbeat lists the new `kid`; a copy that stops (scaled down, restarted) drops out when its entry expires, and a new one starts from the current Secret, so it has the key. While waiting, encryption continues with the current key, so nothing breaks; `rotation.waitingFor` names the copies that don't have the new key, and the console shows "waiting for N copies to load the new key", with their names. After `config_encryption:activation:warn_minutes` (15) it also shows a warning (logged once), saying that the usual cause is a node whose kubelet hasn't refreshed the Secret (or, with OpenBao, External Secrets not syncing) and that restarting the named pods resolves it. It **never activates on a timeout**, since a copy without the key couldn't read what the others then write. When all have it, the server sets `ConfigKeyState.activeKid`, audits `CONFIG_KEY_ACTIVATED` and publishes the notice; every copy then encrypts with the new key (one that missed the notice reads `activeKid` on its next keyring reload, within a minute, and until then still encrypts with a key every copy has).
     - **"Activate anyway"** (`POST system/config-keys/activate` with `{ kid }`, 10.5; trusted role and elevation, audited `CONFIG_KEY_ACTIVATION_FORCED` with the copies that hadn't loaded the key) is for an admin who knows a stale copy is being replaced. It activates at once, in one versioned update of `ConfigKeyState` (setting `activeKid`, `activatedAt` and `rotation.activationForced`), and publishes the notice. A stale copy still encrypts with the old key (its ring lacks `activeKid`, so it keeps the newest key it has, 5.3), which every copy can read, but it can't read a value the others save with the new key until it is replaced (it shows "can't be read", 5.4). The console asks the admin to confirm that, naming the copies. It changes nothing else: steps 3 and 4 keep their conditions, so re-encryption, which would make every existing value unreadable to the stale copy, still waits until it is gone or has loaded the key.
  3. **`reencrypting`.** Once every live heartbeat lists the new `kid` and reports it as the one it encrypts with (so no copy can still write with an old key or fail to read the new one; after "Activate anyway" this waits for the stale copies to go), the job re-encrypts every envelope whose `kid` isn't the active one, page by page (`config_encryption:reencrypt:batch_size`, 100 rows), each row in one version-checked update; a row changed meanwhile is left for the next run, never overwritten. It decrypts and encrypts in process. The plaintext doesn't change, so no cached value needs dropping, and a plugin row's re-encryption leaves the plugin-state hash as it was (5.7); the rows' new versions still reach the integrations layer's version timer, which only rebuilds it. Each full pass records the counts per `kid` on `ConfigKeyState` and audits `CONFIG_REENCRYPTED` with counts when it changed anything. An envelope it can't decrypt is left, counted under its `kid` and named in the console; that only happens after a restore with an older keyring (5.9).
  4. **`retiring`.** As soon as a full pass that started after step 3's condition held finds no envelope on an old `kid`, the server removes the old key from the ring (the same version-checked write as step 1) and audits `CONFIG_KEY_RETIRED`. **The same for both kinds of rotation:** a compromised rotation's old key goes immediately after re-encryption, and a normal one's also automatically once unused, with no extra wait. A `kid` still counted (an envelope that couldn't be decrypted) is never removed, the active key is never removed, and the ring is never left empty. Then `phase` is `done`.
- **"Key compromised"** (`compromised: true`) runs the same steps; it is recorded on the rotation and in the audit, the server runs step 3 batch after batch without waiting for the next run, and the console reminds the admin that a keyring exposed together with a database copy has exposed the secrets themselves, so the credentials should be replaced at their providers too.
- **One rotation at a time** (approved 2026-10-28): a request while one is in progress is answered 409 with the progress, except that `compromised: true` marks a running normal rotation compromised. A failed rotation (`failed`, only for a ring that can't be read or parsed) is shown with its error and can be started again.
- **The console** (`GET system/config-keys`, 10.5) shows the ring's `kid`s with their age and envelope counts (never key material), which one is active, and the rotation's phase and progress.

Adding: a key already in the ring that is newer than the request is the one a copy that crashed before recording it had written, and is taken up instead of a second (its `CONFIG_KEY_ROTATED` is audited by the copy that takes it up). Activating and re-encrypting need at least one live heartbeat: with none, or with the heartbeats unreadable, the rotation waits and says why in `lastError`. A pass is one run, however many pages (`reencrypt:batch_size` rows each, read by `uid` after the last row of the page before, never by offset, so a row deleted or added meanwhile can't make a page skip one): a normal and a compromised rotation differ only in what they record and audit. A pass records `kidUsage` and `reencryption` on its row, and moves the rotation to `retiring` only when it saw every row and saved every change; retiring removes every key but the active one that has no counted envelope (never the active key, so never an empty ring), refuses while `kidUsage` is unrecorded, and ends the rotation `done`, with a `lastError` naming the key, when an envelope that can't be decrypted keeps one in the ring. A copy that can't encrypt with the new key itself waits too. A row that can't be saved for a reason other than a lost race is named (`<record> '<uid>'`, the first five, never a value) in the rotation's `lastError` until a later pass saves it, and a pass that throws is recorded there as well, so a rotation stuck in `reencrypting` always says why.

### 5.6 Rules

- **Write-only API.** No route returns a secret value or an envelope. Responses carry `{ "secret": true }` per set field (`src/secrets/SecretMask.ts`: `secretMask()`, `isSecretMask()`, `maskSecretSettings()`) and accept that mask back as "unchanged"; `null` clears. `toSecretPatch(input, fields, multiLineFields?)` still turns a write-only form's credentials into the change to apply: a string sets (surrounding whitespace, such as a pasted newline, trimmed), `null` clears, the mask or an absent field is left alone; an empty value, a control character outside `multiLineFields` (Google's `serviceAccountJson`), any other value and an unknown field are a 400 that names the field and never repeats what was sent. `maskSecretRef(ref)` becomes `maskCredentials(credentials)`, each field present shown as the mask.
- **Never logged or audited**: plaintext appears in no log line, audit entry or error message, and an envelope in none either.
- **Hidden from Diagnostics**: every config key the integrations layer sets that holds a secret is named on `hiddenSettings.ts`'s explicit list (`giphy:api_key`, `system:plugins:registry_token` and `system:plugins:namespaces` already are), and so is `config_encryption:keyring`. The Diagnostics page shows the integrations layer as its own source, secrets as "set", and the keyring's `kid`s, ages and envelope counts.
- **Key and data apart:** only the server pods hold both the keyring and database access, and only the server can change the keyring (5.5). The controller and external-dns never see the keyring.

### 5.7 Plugin secret settings

**Decided by JP (2026-10-28):** plugin settings stay in the `Plugin` row; the ones `isSecretSetting()` classifies as secret (manifest `secret: true`, `type: "password"`, or the key words) are stored encrypted in place (associated data `Plugin`, the row's `uid`, `settings.<key>`). A package has one row whose `uid` survives version changes, removal and revival, so its envelopes stay valid.

- **Saving:** every save path (`PUT /:id`, a value carried to a new version, a plugin's add and revival with a manifest's default, an uploaded pack's replacement, and the server's seeding of default plugins) encrypts a secret setting's value before the one row write, **once `ConfigKeyState.pluginSecrets.encryptedAt` is set** (4.9). Until the first encryption run has completed (below), a secret setting is saved in plaintext as today, so a pod of the previous release, still running during the rollout, is never handed an envelope; the encryption run then encrypts it. The mask sent back keeps the stored envelope; an envelope sent as a value is an object, which no setting type takes (400), so a setting can never be pointed at another secret.
- **A version change** keeps the envelopes of the settings the new version still declares and, when a setting's definition takes other values than before (its `type`, `min`, `max` or `options` changed; a new label or description doesn't count), decrypts the kept value and checks it as a saved value is: a 400 for a value the new version no longer takes ("'PIN' must be a number."), never naming it; a 503 asking for a new value when it can't be decrypted.
- **Loading:** the server's plugin host decrypts each envelope while building the `plugins` config layer at worker start, so plugins still receive plaintext and see no change; a plaintext value (before the encryption run) is used as it is. One that can't be decrypted is left out (the deployment's value or the plugin's default applies) and named, without its value, in a warning.
- **The state hash** (`computePluginStateHash()`, **decided by JP, 2026-10-28**) counts a secret setting by its decrypted value, as it counted every setting before restapi step 7, so a new value reloads the plugins while the encryption run and the rotation's re-encryption, which leave the plaintext unchanged, don't. The hash is published on Redis and returned by the plugin status route, as it was then.
- **The plugin route's write-only masking** behaves exactly as today, and an uninstall strips every secret setting from the removed row, as built.
- **The encryption run** (`PluginSecretEncryptor`, Mongo and SQL, `await encryptor.run()`, never throws; it replaces step 7's `PluginSecretMigrator`) encrypts every installed plugin's secret settings still in plaintext, page by page, one version-checked update per row (a row changed meanwhile is read again, at most 3 attempts), and removes an uninstalled plugin's plaintext secrets instead. It is idempotent (an envelope is left alone), safe across server copies (under a Redis lock, one copy at a time), audits `PLUGIN_SECRET_MIGRATED` per key without values (`dropped: true` for a removed one), and logs the counts (`{ encrypted, dropped, remaining }`). The production key guard (5.2) means it always has a key. Because the hash counts decrypted values, it rolls no plugin worker.
- **It waits for the rollout** (**decided by JP, 2026-10-28**, replacing the release-note requirement first proposed): a server from before this release applies `row.settings` raw, so it would hand a plugin an envelope as a setting's value. Until `ConfigKeyState.pluginSecrets.encryptedAt` is set, the server starts it in the background after the datastores connect (never delaying startup or the plugin host, which reads plaintext as it is) and it encrypts only once **every pod of the server Deployment runs this release**, checked every 30 s through the server's existing read-only Kubernetes access (the Diagnostics Role's `get`/`list` on `pods`): the server reads its own pod (`HOSTNAME`), lists the pods matching the Deployment's selector (`config_encryption:plugin_secrets:pod_selector`, which the chart renders from the server Deployment's selector labels), and proceeds only when every one of them, terminating ones included, carries its own pod's `pod-template-hash`, i.e. no pod of an older ReplicaSet is left; a pod that has finished (`Succeeded` or `Failed`, such as an evicted old one, which Kubernetes keeps listed) runs nothing and is not waited for. (The Deployment's own `observedGeneration`/`updatedReplicas` aren't readable with that Role, which has no `deployments` rule; the pod check is the same condition: no pod from before the rollout.) Its first completed run sets `encryptedAt`, from which point saves encrypt and every later start runs it at once (any later release understands envelopes). While waiting, `pluginSecrets.reason` says why (old pods, by name, or the pods can't be listed) and Diagnostics shows it; a failed listing (the Diagnostics Role turned off with `global.diagnostics.rbac.create: false`) is logged once and retried, and `config_encryption:plugin_secrets:wait_for_rollout: false` skips the check for an operator who has checked the rollout. Outside Kubernetes (no ServiceAccount token: `yarn dev`, docker-compose) it runs at once. On powerlevel.gg (one replica, `Recreate`, no stored secret plugin setting) it runs immediately and changes nothing. A downgrade to a release before this one after the run isn't supported, as for any data migration.
- **As first built** (restapi step 7, `cbfe83b`): `PluginSettingValue` with `{ "$secretRef": SecretRef }`, `PluginSecretUtils` (a store path per write capped at 253 characters, `storePluginSecretSettings()`, `writePluginSecretSetting()`, `resolvePluginSecretSettings()`, `releasedPluginSecretRefs()`, `plaintextSecretKeys()`/`plaintextPluginSecrets()`), the hash by reference, the rollback re-read of references, `checkKeptPluginSecrets()` reading kept values from the store, and `PluginSecretMigrator`. Reworked as above (18, R4, implemented): `isSecretSetting()` in `PluginUtils`, the version-change check, `withoutSecretSettings()`, the mask handling and the plaintext-key helpers stay; store paths, references and their cleanup went.
- **As implemented (restapi R4).**
  - **Files:** the helpers are in `src/plugins/PluginUtils.ts` (`PLUGIN_SECRET_RECORD`, `pluginSecretField()` and `pluginSecretContext()` giving the associated data of 5.2, `resolvePluginSettings()`, `computePluginStateHash()`) and `PluginSecretUtils.ts` (`sealPluginSecretSettings()`, `checkKeptPluginSecrets()`, `plaintextSecretKeys()`, `withoutSecretSettings()`); `pluginEnvelopeSource()` (`PluginEnvelopeSource.ts`) is what `ConfigKeyRotationJobMongo`/`SQL` register for `Plugin`; `ServerRolloutCheck.ts` has the interface, `NullServerRolloutCheck` and `resolveServerRolloutCheck()`; `PluginSecretEncryptor` is in `src/util` with `PluginSecretEncryptorMongo`/`SQL`. `SecretStore`, `NullSecretStore`, `SecretRef`, `SecretBackend`, `PluginSecretSettingRef`, `isPluginSecretRef()`, `PluginSecretMigrator` and the store paths and writes of `PluginSecretUtils` are gone; `PluginSettingValue` is `string | number | boolean | ConfigEnvelope`.
  - **Saving:** `BasePluginRoute` injects `ConfigCipher` and reads `ConfigKeyState.pluginSecrets.encryptedAt` through `configKeyStateClass`, which `PluginRouteMongo`/`PluginRouteSQL` supply (a route built on the abstract class supplies it too). It reads it at every save that holds a plaintext secret, never remembers it, and a state row it can't read fails the save rather than saving a secret in plaintext. Settings are sealed before anything is written, so a server with no cipher answers `503` ("Configuration encryption isn't available on this server, so plugin secret settings can't be handled.") and one with no keyring answers the cipher's `503`, with nothing changed; a save with no secret in it needs neither. A manifest default is sealed under the uid the row will have (a revived row keeps its own). The version-change check decrypts a kept value only when its setting's `type`, `min`, `max` or `options` changed; one it can't decrypt is a `503` ("The saved value of 'PIN' can't be read to check it against this version. Save a new value for it.").
  - **The hash and the plugin host:** `computePluginStateHash(plugins, cipher?)` counts a secret by its decrypted value and leaves out one it can't decrypt (and every envelope when it has no cipher), exactly as `resolvePluginSettings(row, cipher)` leaves it out of the settings the plugin host loads (`{ values, unresolved }`), so every copy hashes what it loads. The route passes its cipher; the server's `PluginHost`, `PluginWatcher` and `PluginPurger` must pass theirs (S2), or their hash of a row with an envelope would differ from the route's.
  - **`PluginSecretEncryptor`:** `run()` never throws and answers `{ encrypted, dropped, remaining, completed, waiting? }`: `completed` is whether `encryptedAt` is set afterwards, `waiting` why it did nothing (the rollout check's reason; no cipher registered; another copy holding the lock). It takes the same lock as the key rotation (`ConfigKeyChannel.acquireLock()`; where no channel can be had it runs unlocked, the version checks keeping it safe) and records `encryptedAt` (with `waitingForRollout: false`, no `reason`) once no row stays in plaintext, leaving a run another copy recorded meanwhile alone. While it waits it writes `pluginSecrets { waitingForRollout: true, checkedAt, reason }` only when the reason changed or the last write is five minutes old. `ServerRolloutCheck.check()` answers `{ rolledOut, reason? }`; one that rejects counts as unfinished ("the pods can't be listed"), logged once. `resolveServerRolloutCheck()` falls back to the check that answers "rolled out" only for a server that registers none and doesn't run in Kubernetes (`KUBERNETES_SERVICE_HOST` unset); a registered class that fails to build or start, or none registered inside Kubernetes, gives `UnavailableServerRolloutCheck`, which rejects, so the encryptor waits and the failure is logged. The waiting record never replaces an `encryptedAt` another copy wrote. `config_encryption:plugin_secrets:wait_for_rollout` is read by the encryptor itself. `runUntilEncrypted({ intervalMs = 30 s, signal })` is the server's background loop: it repeats `run()` while it waits, which includes a datastore that failed to answer and a key state row that couldn't be saved, and returns on the first run that completes or ends without waiting (a row that couldn't be saved is for the next start). After recording `encryptedAt` the run looks at the rows once more, under the same lock, for a save that read the state before it was set. The window that remains is one save that read the state row before `encryptedAt` was set and writes after that last look (milliseconds, on a new-release route or while `wait_for_rollout` is false): its plaintext secret stays until the next start's run, which every later start performs at once.

- **As first built (server step 2)** the server's policy also had `create`/`update`/`patch`/`delete` on `kv/data/<fullname>/integrations/dns/*` and read-write on `.../server/*` and `.../plugins/*` (with `read`/`delete` on their metadata) for the secret store, the ESO policy `read` on `.../integrations/dns/*`, and a fourth role, `<fullname>-dns-controller` (`read` on `kv/metadata/<fullname>/integrations/dns/*`, to roll a pod on new credentials). The controller no longer touches credentials in OpenBao and the server stores none there, so the rework removes those paths and that role, and the installers rewrite the policies and delete the role and its policy from an existing vault (18).
- The installer migrates the two existing periodic tokens to the same scheme: the chart's `SecretStore` switches to `auth.method: kubernetes` with the `<fullname>-eso` role, the PKI client logs in with the server role, and the old tokens and their Secrets are revoked and deleted.
- **As implemented (server step 2).**
  - **Roles:** each bound to one ServiceAccount and the release namespace, `audience=openbao`, `token_ttl` and `token_max_ttl` 1 hour (a client logs in again rather than renewing); the server's is the chart's ServiceAccount (`<fullname>` by default), External Secrets' is `<fullname>-openbao-eso`, which the chart creates (`automountServiceAccountToken: false`; External Secrets requests its tokens, with `serviceAccountRef.audiences: [openbao]`). Each role has a policy of its own name.

Config: `mail:pki:openbao:{ca_file,auth:{method,role,mount_path,token_file}}`; `method` "token" (the default) keeps `mail:pki:openbao:token` working for a vault prepared by hand. `OpenBaoClient` stays for the PKI CA and also writes the keyring's KV path during a rotation (5.5); delivering the keyring to the pods stays External Secrets' job.
  - **Settings for the secret store, removed in the rework:** server step 2 also added `mail:secrets:openbao:{address,token,timeout_ms,ca_file,auth:*}` for the secret store's OpenBao backend, `mail:secrets` to `PROTECTED_PLUGIN_SETTING_KEYS`, `mail:secrets:openbao:token` to Diagnostics' hidden list, and the chart's `mail__secrets__openbao__*`. With no secret store they have no reader and go (18).
  - **The chart never used the PKI token:** it never set `mail__pki__backend`, and the `openbao.pki.tokenSecret` it read had no default, so the Secret was never loaded (and `global.openbao.enabled` without the installer's `openbao.pki.*` values failed to render). Its revocation therefore changes nothing that runs; `openbao.pki.tokenSecret` is gone, and `openbao.auth` (`method: kubernetes`, `role` defaulting to `<fullname>-server`, `audience`) gives the server pod a projected token for the audience `openbao` at `/var/run/secrets/openbao/token` and sets `mail__pki__openbao__*`. The chart refuses it for a pod running as the namespace's `default` ServiceAccount (unnamed or named `default`), which every other pod shares. For a vault prepared by hand, `openbao.auth.method: token` gives the client `mail__pki__openbao__token` from the key `token` of the Secret `openbao.auth.tokenSecret`; the chart refuses those keys in `service.config`, whose ConfigMap is plaintext. The OpenBao CA mount (`global.openbao.caConfigMap`, mounted at `/etc/rapidmx/openbao-ca`) arrives here rather than with the chart step for DNS (S9).
  - **The migration proves the new logins first:** it waits for every `SecretStore` of the release to be Ready (after a short pause, so an old Ready isn't taken for a new one), then has `kubectl create token` mint a 10-minute token of `<fullname>-openbao-eso` and of the server's ServiceAccount for the audience `openbao`, and in the vault's pod logs each in to its role (revoking the token it gets) before revoking the old tokens and deleting their policies; any failure keeps them, and the next run tries again. Every token reaches the pod over stdin, never as an argument.
  - **The bundled auth-server** (a subchart) has a `SecretStore` of its own, reading the same `global.openbao`. It picks up Kubernetes auth and the audience (the server chart's `rrst.vaultAuth` define overrides the subchart's), but it renders no `caProvider`, so it can't verify the TLS listener: **the auth-server chart must render `caProvider` from `global.openbao.caConfigMap`** (for example through a define the server chart can override, as it does `rrst.vaultAuth`), and the server chart's `authserver` dependency must move to that release, before a server release with this installer.
- **TLS on the in-cluster listener.** The installer issues the listener certificate with cert-manager (already installed; `deploy/aws/bootstrap.sh` now installs it whenever it installs OpenBao, also with `RAPIDMX_TLS=false`): a self-signed `Issuer` in the `openbao` namespace creates a CA (`openbao-ca`, ten years, its key kept on renewal so the copy stays valid), a CA `Issuer` issues `openbao-tls` (a year, renewed 30 days ahead) for `openbao`, `openbao.openbao`, `openbao.openbao.svc`, `openbao.openbao.svc.cluster.local`, the pod's internal names, `localhost` and `127.0.0.1` (the `bao` CLI in the pod talks to `https://127.0.0.1:8200`, trusting the CA through `BAO_CACERT`). OpenBao's listener uses it (`tls_cert_file`/`tls_key_file`), and the address becomes `https://openbao.openbao.svc:8200`. The CA certificate is copied into ConfigMap `<fullname>-openbao-ca` in the release namespace; the server mounts it and verifies the peer with it (`mail:pki:openbao:ca_file`), and the `SecretStore` uses it through `caProvider`.
- `assertSafeAddress()` keeps its rule (https to any host, plain HTTP only to loopback) unchanged; with TLS the in-cluster address passes, and the OpenBao clients gain only a configurable CA bundle. An external OpenBao (`OPENBAO_ADDRESS`, `RAPIDMX_OPENBAO_ADDRESS`) must be https; the installer refuses plain HTTP unless the address is loopback, and `OPENBAO_CA_FILE` (`RAPIDMX_OPENBAO_CA_FILE`) names its CA, copied into the same ConfigMap. External Secrets keeps its token Secret there: the installer creates no roles in a vault it doesn't install.

### 5.9 Backups and restore

- **A database backup is useless without the keyring**, so the keyring is backed up with it: the installer's final message (12.3) and the docs say so, as they already do for the OpenBao unseal keys (the Secret `<fullname>-config-keyring`, or the OpenBao KV path).
- A backup restored with an older keyring that lacks a newer `kid` can't decrypt the values written after it: those fields show as "can't be read" (5.4) and must be entered again. A keyring saved once a rotation has removed the old key (5.5) no longer decrypts database backups taken before the rotation, so keyring backups are kept as long as the database backups they serve, and the console says to back up the keyring when a rotation finishes.

## 6. Records

### 6.1 Per domain

For each enabled `Domain` with `dnsProviderUid`, exactly the records `checkDnsSetup()` recommends, built by one shared function (`buildDesiredDnsRecords(domain, ctx)` in `DnsSetupUtils.ts`) that `checkDnsSetup()` is refactored to use too, so the checklist and the publication cannot drift:

| Record | Name | Type | Value |
| --- | --- | --- | --- |
| Ownership | `_rapidmx-verify.<domain>` | TXT | `rapidmx-domain-verification=<token>` (§6.5) |
| SPF | `<domain>` | TXT | **only when `apexTxt.managed`** (DECIDED, §9.4): one endpoint holding `apexTxt.spf` (`v=spf1 mx ~all`, or the existing SPF chosen at opt-in) plus every value on `apexTxt.keep`; otherwise SPF is shown as manual (`apex_txt_unmanaged`) |
| MX | `<domain>` | MX | `10 <mx host>` |
| DKIM (active) | `<dkimSelector>._domainkey.<domain>` | TXT | `v=DKIM1; k=rsa; p=<key>` |
| DKIM (next / previous) | `<selector>._domainkey.<domain>` | TXT | during a rotation only (6.2) |
| DMARC | `_dmarc.<domain>` | TXT | as recommended |
| OpenPGP WKD | `openpgpkey.<domain>` | CNAME | `<mx host>` |
| Autodiscover | `autodiscover.<domain>` | CNAME | autodiscover host, only while the plugin is active |
| Autodiscover SRV | `_autodiscover._tcp.<domain>` | SRV | `0 0 443 <autodiscover host>.`, only while the plugin is active |

Rules:

- A record whose `configured` would be false is not published (no DKIM before a key exists).
- TXT at the same name is one endpoint: external-dns manages a name and type as one record set, and once it owns a set it owns **all** of it (§9.3). That is why ownership verification has its own name (§6.5) and the apex TXT set is never touched without the admin's opt-in.
- The ownership TXT keeps being published after verification (it costs nothing and lets a re-verification work); it is removed with the domain.
- A disabled domain (`enabled: false`) keeps its records; deleting a domain removes them.
- An alias domain publishes its own full set, like any other.
- A kind the provider cannot hold (rfc2136: MX, SRV) is left out and shown as manual (`kind_unsupported`).

`DnsRecordType` gains `dkim_next` and `dkim_previous`, so the checklist shows the extra selectors during a rotation.

### 6.2 DKIM rotation

**Components.**

- **restapi**: the rotation state on `Domain`, `DkimRotationJob`, the routes, an extended `DkimKeyProvider` interface, and `FsDkimKeyProvider`'s per-domain selectors and switch (the class lives in restapi, not the server, so its rotation methods are restapi step 4; first drafted as server step 5).
- **server**: registers `DkimRotationJob` and documents its configuration.
- **postfix-bridge**: `dkim-sync.sh` signs each domain with its own selector and acknowledges the switch.

**Selectors.** Each rotation mints a new selector `rmx<yyyymmdd>` (suffix `b`, `c`, ... on a same-day collision). An existing domain keeps the global selector (`mail`) until its first rotation.

**`DkimKeyProvider` additions** (optional methods; `supportsRotation` false on `NullDkimKeyProvider`):

```ts
interface DkimKeyProvider {
    ensureKeyPair(domain: string): Promise<DkimKeyPair | undefined>;   // unchanged
    readonly supportsRotation?: boolean;
    /** Creates the key for `selector` without signing with it. Idempotent (exclusive create, as ensureKeyPair is). */
    generateKeyPair?(domain: string, selector: string): Promise<DkimKeyPair>;
    /** The key `selector` has, without creating one (added in restapi step 4): what tells a provider-made key from an imported one on rows from
     * before `dkimManaged`. */
    findKeyPair?(domain: string, selector: string): Promise<DkimKeyPair | undefined>;
    /** Makes `selector` the one the MTA signs `domain` with. */
    activate?(domain: string, selector: string): Promise<void>;
    /** The selector the MTA reports it is signing `domain` with, if it reports one. */
    signingSelector?(domain: string): Promise<string | undefined>;
    /** Deletes the private key of a retired selector. */
    deleteKeyPair?(domain: string, selector: string): Promise<void>;
}
```

**Files on the shared DKIM volume** (`FsDkimKeyProvider`, restapi):

- `<domain>.<selector>.key`: one per selector, as today's naming already allows.
- `<domain>.selector`: the selector to sign with, written atomically (temp file + rename) by `activate()`. Its absence means the global selector, so existing deployments are unaffected until a rotation.
- `<domain>.signing`: written by postfix-bridge after OpenDKIM has reloaded with a selector, containing that selector. `signingSelector()` reads it.
- As implemented: `ensureKeyPair()` returns the key of the selector in `<domain>.selector` (the global one without it), `activate()` refuses a selector without a key, `deleteKeyPair()` refuses the selector signing uses and resolves for a key already gone, a selector must be one lowercase DNS label, and a new key has `mail:dkim:rotation:key_bits` bits: a whole number from 2048 to 4096 (or its text), else 2048 with a warning, for every new key, not only rotations. Keys are generated asynchronously (`crypto.generateKeyPair`, on libuv's thread pool), never blocking the event loop.

**postfix-bridge `dkim-sync.sh`** (and the init container): per domain, use `<domain>.selector` when present, else `$DKIM_SELECTOR`; copy `<domain>.<sel>.key` to `/etc/opendkim/keys/<domain>.<sel>.private`; write `KeyTable` lines `<sel>._domainkey.<d> <d>:<sel>:<path>` and `SigningTable` `*@<d> <sel>._domainkey.<d>`; after a successful `SIGUSR1` reload, write `<domain>.signing`. Old `<domain>.private` files are removed once a per-selector file exists. The bundled `postfixBridge` subchart moves in lock-step with the server chart. docker-compose (`server/docker-compose.mail.yml`) uses the same script.

As implemented (postfix-bridge; where it differs from the paragraph above, this is what the chart does):

- **Key layout:** `/etc/opendkim/keys/<domain>/<selector>.private`, not `<domain>.<sel>.private`: a flat name can't be told apart from another domain's `<domain>.private` (`example.co.uk.private` is also `example.co` with selector `uk`). `<domain>/selector` names the one in use, and the tables name only its file. **The key a domain moves off stays** until the server deletes `<domain>.<old>.key` (the end of the overlap, `deleteKeyPair()`, or a cancel) and no longer than the tables of the pass before named it: OpenDKIM reads the key a table names each time it signs, and a milter session opened before the reload keeps the configuration it started with, so deleting it at the switch made such messages fail with "can't load key". Only `<domain>/` directories the script made (with a `selector` file) are touched; opendkim-genkey's `<domain>/<selector>.private` elsewhere is neither read nor removed, as the image never read it either. A domain the server removes keeps its files and table entry (the sender check already stops it sending) and is no longer acknowledged.
- **`<domain>.private` is kept, as a copy of the key in use**, not removed: the `boky/postfix` image checks for it at every start and, with `DKIM_AUTOGENERATE`, generates a key of its own when it is missing (logging "New DKIM keys have been generated! Please make sure to update your DNS records!"). The copy stops that and leaves no retired key behind.
- A domain is one with `<domain>.selector` or `<domain>.<DKIM_SELECTOR>.key` in the shared volume. A selector file that isn't one lowercase DNS label is ignored with a warning, and a selector whose key isn't a complete key yet (`openssl pkey`), leaves the domain on the key it has. A `<domain>.private` of a domain the server has no key for (generated by the image, or put there by hand) is still signed with the global selector.
- **The acknowledgement** is written for each of the server's domains whose `<domain>.signing` doesn't name its selector in the tables yet, **on the pass after** the one that wrote that selector into the tables (one `DKIM_SYNC_INTERVAL`, default 10 s, after `SIGUSR1`), and only while OpenDKIM runs (`pgrep -x opendkim`): it was then either signalled a pass earlier or started after. Not running, nothing is acknowledged; a selector whose key isn't usable yet is never acknowledged. It approximates "after a successful reload": a failed reload isn't detected (the tables are the script's own and every key passed `openssl pkey`), and a session opened before the reload may still sign with the old selector until it closes, which the kept old key and, outside a compromise, the overlap cover; a compromise's zero overlap retires the old record at the job's next run after the acknowledgement.
- **The shared volume is written by the server too**, so only plain files are read from it (not a link, a directory or a pipe; `<domain>.selector` and `<domain>.signing` at most 64 bytes), and `<domain>.signing` is written as an exclusive create under a random name (`mktemp -u`, `set -C`) renamed over it with `mv -fT`, never through a link and never into a directory.
- **`dkim-sync.sh --once`** makes one pass: the init container runs it (into the OpenDKIM keys volume, its tables kept in the container) so the image finds `<domain>.private` and keeps it, and `opendkim.sh` runs it before OpenDKIM starts, so OpenDKIM never starts with the image's tables (the global selector for every domain). Verified against the real image: a live switch signs `s=<new selector>` after the reload, and a restart signs with it from the start.
- **docker-compose:** `server/docker-compose.mail.yml` has no Postfix, and postfix-bridge's own `docker-compose.yml` never had the watcher (its DKIM is the image's own generated key, documented as eval-only), so neither uses the script.

**State** (`Domain.dkimRotation`):

```ts
interface DkimRotationState {
    phase: "idle" | "pending" | "switching" | "overlap";
    next?: { selector: string; publicKey: string; createdAt: Date; liveSince?: Date; reason: "scheduled" | "manual" | "compromised" };
    previous?: { selector: string; publicKey: string; retireAt?: Date };
    reason?: "scheduled" | "manual" | "compromised";   // restapi step 4: the switched rotation's reason, kept until it retires
    switchedAt?: Date;                                  // restapi step 4: when signing switched; the acknowledgement hour counts from it
    lastRotatedAt?: Date;
    lastCancelledAt?: Date;                             // restapi step 4: the interval counts from it too
    paused?: boolean;
    mintedSelectors?: string[];                         // restapi step 4: the selectors minted on the latest start's UTC day, never minted again
    lastError?: string;
}
```

**Phases**, driven by `DkimRotationJob` (`mail:jobs:dkim_rotation:schedule`, default hourly). It runs on every replica; each transition is one versioned update of the domain row, so a replica that loses the race skips:

1. **idle → pending.** Triggered when `lastRotatedAt` (or the key's creation) is older than `mail:dkim:rotation:interval_days` (default 180), or by "Rotate now". The job records `next.selector` in the row first, then calls `generateKeyPair()`. The new record `dkim_next` joins the desired state: published by the provider, or shown in the console for the admin to add ("Publish this record to finish rotating"). Signing is unchanged.
2. **pending → switching.** The job live-checks `next.selector._domainkey.<domain>` through the configured `DnsResolver`. When it matches, it sets `liveSince`. When `liveSince` is at least `mail:dkim:rotation:publish_grace_hours` old (default 48, so receivers' resolvers have dropped any negative-cached answer), it calls `activate()`, sets `dkimSelector`/`dkimPublicKey` to the new key, and moves the old one to `previous`. **A manual domain follows exactly the same rule: signing never switches before the live check passes**, however long the admin takes. The console reminds the admin after 7 days.
3. **switching → overlap.** When `signingSelector()` reports the new selector (postfix-bridge has reloaded), the job sets `previous.retireAt = now + mail:dkim:rotation:overlap_days` (default 7), so mail signed with the old key and still in queues, or re-verified later, keeps verifying. If no acknowledgement arrives within an hour (an older postfix-bridge without the acknowledgement), the job records `lastError`, keeps both selectors published, and does not start the overlap clock.
4. **overlap → idle.** At `retireAt` the old selector's record leaves the desired state (the provider deletes it; a manual domain's console says the admin may now remove it), `deleteKeyPair()` removes the old private key, and `lastRotatedAt` is set.

**Manual action.** `POST mail/domains/:id/dkim/rotate` with `{ compromised?: boolean }` (trusted role and elevation, audited) starts phase 1 now. With `compromised`, the publish grace is skipped (the switch still waits for the live check, since switching earlier makes every message fail DKIM) and the overlap is zero: the old record is removed as soon as signing is confirmed. `POST mail/domains/:id/dkim/rotation/cancel` abandons a rotation whose switch the MTA has not confirmed (deletes the new key and its record; a switch not yet acknowledged is reverted, see below). `PUT mail/domains/:id/dkim/rotation` with `{ paused }` stops scheduled rotation for one domain.

**Not rotated:** domains whose key was imported by hand (`dkimManaged: false`), deployments whose provider does not support rotation (`NullDkimKeyProvider`), and SES deployments (SES's Easy DKIM rotates its own keys). The console says why.

**As implemented (restapi step 4).**

- `DkimRotationJob` (`DkimRotationJobMongo`/`DkimRotationJobSQL`, schedule `mail:jobs:dkim_rotation:schedule`, default `0 0 * * * *`) reads every domain page by page and moves each through as many phases as are due (at most five per run, so a compromised key goes from live through the switch to retired in one run once the MTA has confirmed). A version conflict (another replica, an admin's cancel) is logged at debug level and the domain is looked at again next run; any other failure is a warning and the other domains go on. It does nothing while the provider doesn't rotate or `mail:transport:provider` is `ses`. A provider rotates only with `supportsRotation`, `generateKeyPair()`, `activate()` and `signingSelector()`: without the acknowledgement a switch could never be confirmed.
- **Scheduled starts** need `mail:dkim:rotation:enabled` (the text `false`, `0`, `no`, `off` too turn it off), an enabled and verified domain with a key (nobody may ever publish an unverified domain's new record), no pause, and `interval_days` since the latest of `lastRotatedAt` and `lastCancelledAt`, or since the domain's creation before either. At most `mail:dkim:rotation:max_starts_per_run` (default 10) start per run and replica, so the first run after rotation arrives, when every older domain is due at once, spreads the new keys and records over several runs. With `enabled` off, "Rotate now" still works and a rotation in progress still finishes. A row from before `dkimManaged` is classified first (`findKeyPair()`): a key the provider doesn't hold is recorded as imported and never rotated; a provider without `findKeyPair()` leaves such rows alone.
- **Start:** the new selector (`rmx<yyyymmdd>`, then `b`, `c`, ... `z`, `aa`, ... past the current, previous and next selectors and every selector minted earlier that UTC day, `mintedSelectors`, since a receiver may still cache a cancelled or retired one's record) is recorded with `publicKey: ""`, audited, then generated; a key that can't be generated is kept as `lastError` and retried by the next run. A `next` without a public key is never published. When recording the generated key loses a race (a cancel, another replica), the key is deleted unless the row that won names its selector, so no private key is left behind.
- **pending:** the live check is any TXT at `<selector>._domainkey.<domain>` whose rejoined strings, without spaces, carry `p=<key>`; a record that disappears clears `liveSince`, so the grace starts over.
- **Switch:** one versioned update first sets `dkimSelector`/`dkimPublicKey` to the new key, `previous` to the old one, `reason` and `switchedAt` (so a cancel racing it loses), audited and announced; `activate()` is then called on every run until `signingSelector()` reports the new selector. A failing `activate()`, or no acknowledgement an hour after `switchedAt`, is `lastError`, written only when it changes and cleared once the switch is confirmed. After each `activate()` the job reads the row again and, when a cancel has reverted the switch meanwhile, activates the row's selector instead.
- **Retire:** the row goes back to idle (keeping `lastCancelledAt`, `paused` and `mintedSelectors`) with `lastRotatedAt`, then `deleteKeyPair()` removes the old key; a key that can't be deleted is logged and left.
- **Routes** (`mail/domains`), all trusted-role, the writes with elevation, a 409 for a domain whose key can't rotate (with the reason) or a rotation in the wrong phase:
  - `GET /:id/dkim/rotation` answers `{ rotation, rotatable, blocker?, nextScheduledAt? }`, `blocker` being `unsupported`, `ses`, `no_key`, `imported` or `unknown_key`; `nextScheduledAt` only while the job would start one (idle, not paused, enabled and verified, scheduled rotation on). It writes nothing.
  - `POST /:id/dkim/rotate` `{ compromised?: boolean }` starts a rotation (`reason: "manual"` or `"compromised"`) and answers the domain with `next` filled in. During a rotation, `compromised: true` means the key being rotated away is compromised (audited again as `DKIM_ROTATION_STARTED`): a pending rotation skips the grace, a switching one gets no overlap (the old record goes as soon as the MTA confirms), and an overlap is retired at once (old record and key). A rotation already treating the key as compromised, or any other rotate during a rotation, is a 409.
  - `POST /:id/dkim/rotation/cancel` abandons a rotation the MTA hasn't confirmed (sets `lastCancelledAt`, deletes the new key, audited, announced) and changes nothing without one. A pending rotation simply ends. A switching one is **reverted**, the way out of a switch the MTA never acknowledges: the provider signs with the old key again (refused with 503, changing nothing, when it can't; 409 when the old key is gone), then one versioned update puts `dkimSelector`/`dkimPublicKey` back to `previous` (a job confirming the switch at the same time wins, and the provider is pointed back at the row's selector), then the old key is activated once more; audited with `reverted: true`. An overlap is a 409: it finishes on its own.
  - `PUT /:id/dkim/rotation` `{ paused: boolean }` pauses or resumes scheduled rotation (audited `DKIM_ROTATION_PAUSED`); a rotation in progress still finishes.
- A `PUT` changing `dkimSelector` or `dkimPublicKey` is a 409 while a rotation is in progress, and records `dkimManaged: false` otherwise. `dkimManaged` is server-managed like `dkimRotation`.

**Config:** `mail:dkim:rotation:enabled` (default true), `interval_days` (180), `overlap_days` (7), `publish_grace_hours` (48), `key_bits` (2048), `max_starts_per_run` (10, restapi step 4). These are deployment config, not Integrations.

### 6.3 The deployment's own hosts

Published through the provider config whose `zones` cover each host name:

| Host | Type | Value |
| --- | --- | --- |
| `mail.<global.domain>` (the chart's mail host, `mail:dns:mx_hostname`) | A / AAAA | the deployment's public addresses (6.4) |
| `auth.<global.domain>` | CNAME | mail host |
| `autodiscover.<global.domain>` | CNAME | mail host (when the autodiscover plugin is active) |

A host that a domain's endpoint set already publishes (the deployment's own domain publishes `openpgpkey.<domain>` and `autodiscover.<domain>` itself, 6.1) is left out of the hosts' sets, and so is any host record that would put a CNAME next to another record a domain publishes at that name: two `DNSEndpoint`s claiming one name and type would make its ownership record flip between them, could set two external-dns instances against each other, and deleting the domain would delete a record the hosts still want. Once no domain publishes it, the hosts' set does.

The host list is not hard-coded in the server: the chart renders it into `mail:dns:publish:hosts` (JSON list of `{ name, type: "address" | "cname", target? }`), from the same values that render the Gateway listeners and Certificates, so a host is published exactly when the chart serves it. **A host outside every provider's zones stays manual** (`manualReason: "outside_zones"`) and is marked so in the console and in the installer's final message.

### 6.4 Public addresses

The A/AAAA targets come from `mail:dns:publish:addresses` (JSON list of IPv4/IPv6 literals), which the chart takes from `dns.publicAddresses`. The installer detects them: the node's global unicast addresses (`ip -j addr`), and, when the node has only private addresses (NAT, cloud), the address seen from outside, the way coturn's `detect-external-ip` does. It prints what it found, and `--public-address <ip>` (repeatable) overrides detection. The server validates the list (global unicast only; private, loopback, link-local and CGNAT ranges refused) and publishes nothing for the hosts while it is empty, saying so in the console.

### 6.5 Ownership verification name (DECIDED)

**Decided by JP (2026-10-27):** the ownership TXT moves from the apex to a dedicated name, `_rapidmx-verify.<domain>`, so RapidMX never takes over a domain's apex TXT set to verify it. The takeover spike (§9.3) showed that owning a set means owning every value in it, so publishing the token at the apex would have put every site-verification and SPF value of every domain under RapidMX's control.

- **Value unchanged:** `rapidmx-domain-verification=<verificationToken>` (`buildVerificationTxtValue()`), only the name changes. A new helper `buildVerificationRecordName(domain)` returns `_rapidmx-verify.<domain>`; `DOMAIN_VERIFICATION_RECORD_LABEL = "_rapidmx-verify"`.
- **Recommended and published: only the new name.** `checkDnsSetup()`'s `ownership` row and `buildDesiredDnsRecords()` both use `_rapidmx-verify.<domain>`. The label starts with `_`, so it can never collide with a host name and needs no CNAME exception.
- **Migration: both locations are accepted during a transition.** `findDomainVerification()` resolves `_rapidmx-verify.<domain>` and the apex at once and verifies on an exact token match at the record, or at the apex while `mail:domain_verification:accept_legacy_apex` is true (default true; `false`, `0` and the text `false`, `0`, `no` or `off`, as an environment variable sets it, turn it off: `acceptsLegacyApex()`). The result says where it was found (`location: "record" | "legacy_apex"`, plus `atRecord`/`atLegacyApex`), and `DOMAIN_VERIFIED`'s audit details carry it. `checkDomainVerification()` keeps its boolean answer for existing callers. **The key is not `mail:domains:verification:...` as first drafted:** `mail:domains` becomes the list of seeded domains (§13), and a list can't also hold a nested key.
- **Console:** an unverified domain whose token is found only at the apex is verified as today, and its `ownership` row says "Found at the domain's root (the old location). Publish it at `_rapidmx-verify.<domain>`; the root value can then be removed." A verified domain stays verified (`verified` never flips back), so existing domains need no action; the hint about removing the old apex value is shown while it is still present.
- **Ending the transition:** the default of `mail:domain_verification:accept_legacy_apex` flips to false in a later minor release, announced in the release notes one release ahead. Only unverified domains are affected by the flip.
- **Takeover interaction:** when an admin opts a domain into apex TXT management (§9.4), any `rapidmx-domain-verification=` value at the apex is **not** carried into `apexTxt.keep`; it is dropped, since verification no longer reads it there once the domain is verified.
- Tests (restapi): verification at the new name, at the legacy apex with the flag on, refused at the legacy apex with it off, chunked TXT at both, NXDOMAIN at one location and a match at the other, the `location` reported, and the checklist recommending only the new name.

## 7. The DNS Controller

### 7.1 Why a separate pod

Creating Deployments, Secrets and Jobs is a namespace-admin-like right: whoever holds it can run arbitrary pods in the namespace. The mail server is the large, internet-facing process. It therefore keeps **only its existing read-only Kubernetes access** (the Diagnostics Role) and records desired state; a small controller holds the write rights and nothing else (no database, no Redis, no plugins, no mail).

### 7.2 A dedicated project: `rapidmx/dns-controller`

**Decided by JP (2026-10-27):** the controller is its own project, repository `rapidmx/dns-controller` (`D:/github/rapidmx/dns-controller`), published as the container image `ghcr.io/rapidmx/dns-controller:<version>`. It is **not** the server image with another command: an image that holds the whole mail server (its routes, datastore drivers, plugin host and every dependency of them) in the one pod that can create Deployments, Secrets and Jobs would defeat the point of a separate controller. It follows how `postfix-bridge`, `ses-bridge` and `acme` are separate repositories.

**Runtime.**

- TypeScript on Node.js 24, like `postfix-bridge` (the closest sibling: a small, standalone Node service with one job). Built with `tsc`, linted and tested with the siblings' eslint and vitest setup, 100 % coverage thresholds.
- **No runtime dependencies.** Kubernetes REST through `node:https` with the pod's ServiceAccount token (re-read on every request; bound tokens rotate) and the cluster CA from the ServiceAccount mount, as the server's `KubeClient` does. Not `@kubernetes/client-node` (a large dependency tree in the most privileged pod, for a handful of verbs on six resource types). Not the global `fetch` for Kubernetes either: `fetch` cannot take a per-request CA without the `undici` package's dispatcher, and `NODE_EXTRA_CA_CERTS` would make the cluster CA trusted for every outbound call the process makes; `node:https` keeps the cluster CA scoped to the API server. The server's internal API is called with the global `fetch`. Logging is a small JSON-lines logger, and the health endpoints are `node:http`; the controller serves nothing else (it has no API of its own, 7.3).
- **Image:** multi-stage; built on `node:24-trixie-slim`, shipped on `gcr.io/distroless/nodejs24-debian13:nonroot` (Node only: no shell, no package manager, uid 65532), containing only `dist/` and `package.json`. The pod runs non-root with a read-only root filesystem, all capabilities dropped, `RuntimeDefault` seccomp and `allowPrivilegeEscalation: false`; it writes nothing to disk.
- **Phases of the controller project** (each a reviewed, tested commit series in that repository):
  - **C1 skeleton** (scaffolded 2026-10-27, not yet released): configuration from the environment, JSON logging, `/healthz` and `/readyz`, the Kubernetes REST client, the Lease-based single writer, the versioned API types and the startup handshake (7.3). No reconcile logic.
  - **C2 desired state and auth** (implemented 2026-10-27, not yet released): the desired-state long poll, the controller's own status reports (its version, the desired-state version it has, its Lease), the controller's own projected token on its calls, and (as first built) projected-token verification of the server's calls against the in-cluster JWKS on an internal API of its own, which the rework removes (decided 2026-10-28; 7.3, "As implemented in dns-controller C2"; 18). First drafted as "C2 auth and secrets" with the long poll and status reports in C3; the secret routes moved to C3, next to the other Kubernetes writes.
  - **C3 reconcile:** manifests (external-dns Deployments, `DNSEndpoint`s, each provider's credentials Secret) with server-side apply, image-pin enforcement, the per-provider, per-endpoint and per-operation entries of the status report, and fetching each provider's credentials from the server to write its Secret (7.3, 7.4). The manifests, their apply and pruning and the image pin are implemented (not yet released; 7.4, "As implemented in dns-controller C3"), first with an `ExternalSecret` per provider for credentials kept in OpenBao, which the rework (dns-controller D2, implemented; decided 2026-10-28, §5; 18) replaced with the credentials fetch; the status report's entries are implemented (D3; 7.3, 7.7), except that the server doesn't yet store the provider entry's `lastRolloutAt` (18.2). First planned with `PUT`/`DELETE /v1/secrets/:path` routes for a Kubernetes-Secret backend of the secret store, dropped with that store.
  - **C4 operations:** the takeover, test and restore Jobs (§9). Implemented (D4; 9.3, *As implemented in dns-controller C4*), not yet released.
  - **C5 health:** external-dns metrics scraping and per-provider health in the status report.

**Packaging: a plain image the server chart templates, not a subchart** (recommended). `postfix-bridge` is a subchart because it is a product of its own: it runs its own Postfix, is documented to run without the server chart, and its values make sense alone. The controller has no standalone use. Everything it is configured with derives from the server release: the desired-state URL, the token audience, the Lease and resource names (`<fullname>-...`), the external-dns ServiceAccount and Role. A subchart would need all of that passed down through `global` values, and the controller's Role, the most security-sensitive object in the release, would live in another repository, outside the server chart's `helm template` tests (server Role has no write verbs; controller Role is namespaced and minimal). So the controller repository publishes **only the image** (its publish job mirrors `postfix-bridge`'s `publish-docker-image`, without the chart job), and the server chart owns its templates: `helm/templates/1_deployments/dns-controller.yaml` (Deployment) and `0_config/dns-controller-rbac.yaml` (ServiceAccount, Role, RoleBinding, and the external-dns ServiceAccount/Role of 7.4). Nothing calls the controller, so it has no Service and no NetworkPolicy admitting the server (decided 2026-10-28). The Lease is not templated: the controller creates it.

**Version pin, lock-step.** The server chart pins the controller image to an exact released version, `dns.controller.image.tag` (and optionally `digest`), the way it pins `postfix-bridge` through its `Chart.yaml` dependency version. Releasing a server version that needs a controller change means releasing the controller first and moving the pin in a reviewed commit, edited by YAML key path, never by matching version text. The API handshake (7.3) catches an override that pairs incompatible versions.

**Deployment shape** (rendered when `dns.publishing.enabled`): `replicas: 1` (not configurable), `strategy: Recreate`, its own ServiceAccount `<fullname>-dns-controller` with a projected token volume for the audience `rapidmx-internal-dns` (in addition to the default token used for the Kubernetes API), small requests/limits, and health (`/healthz`, `/readyz`) on port 8081 for the kubelet's probes, its only listener. No Service, no internal API port, no NetworkPolicy admitting the server (as first built: a ClusterIP Service on port 8080 for the controller's internal API and a NetworkPolicy admitting only the server pods on it, removed by JP's decision of 2026-10-28, 18).

**Single writer.** One replica with `Recreate`, plus a `coordination.k8s.io/v1` `Lease` (`<fullname>-dns-controller`, renewed every 10 s, 30 s duration) that the controller must hold before writing, so a stuck old pod and a new one can never write together. Expiry is judged the way client-go's leader election does: by the local time at which this process last saw the Lease record change, not by comparing `renewTime` with its own clock, so clock skew between nodes cannot make two holders. A controller that fails to renew before the duration elapses stops writing at once.

### 7.3 How it gets desired state: a versioned internal API on the server

The controller reads desired state **through the server's internal API**, not from the database:

- **Least privilege.** A database connection would give the pod that can run arbitrary pods read access to every mailbox. The API gives it exactly the desired state.
- **One source of record-building logic.** `buildDesiredDnsRecords()`, assignment rules and the rotation state stay in restapi and the server; the controller only turns desired state into manifests.
- Both backends (Mongo, SQL) work without the controller knowing either.

**Versioning.** The controller and the server ship from different repositories, so their contract is explicitly versioned:

- Every route is under a version path, `/internal/dns/v1/...`, and **every payload, request and response, carries `apiVersion: "dns.rapidmx.io/v1"` and a `kind`**. A receiver refuses a payload whose `apiVersion` it does not speak (`400 { "reason": "unsupported_api_version", "supported": [...] }`) and never guesses.
- Within `v1`, changes are additive only: new optional fields, new `kind`s, new routes. Receivers ignore unknown fields. A breaking change is `v2`, under `/internal/dns/v2`, and the server serves the previous version as well for at least one release, so either side can be upgraded first.
- The types live in the controller repository (`src/api/v1.ts`) and are mirrored in restapi (`src/dns/DnsDesiredStateApiV1.ts`); a contract test in each repository checks the same recorded JSON fixtures.

**Startup handshake.** Before it does anything else, and again every 60 s while it is incompatible, the controller calls the one route whose shape never changes:

| Route | Body | Answer |
| --- | --- | --- |
| `POST /internal/dns/handshake` (unversioned on purpose) | `{ kind: "Handshake", controllerVersion, apiVersions: ["dns.rapidmx.io/v1"] }` | `{ kind: "HandshakeResult", serverVersion, apiVersions: [...], selected?: "dns.rapidmx.io/v1", compatible: boolean, reason? }` |

- The server picks the highest version both list. With none in common it answers `compatible: false` with the reason, and **records the controller's report** (versions, the reason, the time) so the console's DNS providers page and Diagnostics show, for example, "DNS controller 0.4.0 speaks dns.rapidmx.io/v2; this server speaks v1. Install matching versions."
- An incompatible controller **refuses to act**: it does not take the Lease, writes nothing to Kubernetes, fetches no credentials, logs `dns_api_incompatible` at error level, reports not ready on `/readyz` (visible in `kubectl get pods` and in Diagnostics), and retries the handshake every 60 s, since a rolling upgrade of the other side may fix it. A server that cannot be reached is not a mismatch: the controller keeps retrying with backoff and stays ready.
- The controller sends its `apiVersion` on every later call, and the server re-checks it, so a server rolled back underneath a running controller is caught on the next call, which sends the controller back to the handshake.

Routes (restapi `BaseDnsDesiredStateRoute`, mounted by the server under `/internal/dns`, outside the public Gateway like `/internal/mta`; the `v1` types are mirrored in `src/dns/DnsDesiredStateApiV1.ts`, and `test/fixtures/dns-api/v1/*.json` are byte-identical copies of the controller's `test/fixtures/api/v1/*.json`):

| Route | Purpose |
| --- | --- |
| `POST /internal/dns/handshake` | Above. |
| `GET /internal/dns/v1/desired-state?since=<version>` | `kind: "DesiredState"`: provider configs (with the names of their saved credential fields and their `credentialsGeneration`, never values), endpoints per domain and for the hosts, the owner id, the image pin, and queued operations (test, takeover, restore). With `since`, a long poll that answers when the version moves past it, or after 55 s. |
| `PUT /internal/dns/v1/status` | `kind: "StatusReport"`: per provider (Deployment readiness, metrics, last error), per endpoint (applied generation, `observedGeneration`), per operation (result), and the controller's Lease state. Answered `{ apiVersion, kind: "StatusReportResult" }`. |
| `GET /internal/dns/v1/providers/:uid/credentials` | `kind: "DnsProviderCredentials"`: `{ providerUid, generation, values: { <field>: <plaintext> } }`, the provider's credentials decrypted (5.4), for the controller to write the one Secret external-dns reads (7.4). The controller's token only (the same check as every `/internal/dns` route); 404 for a config that is gone, `values` empty for one without credentials; a field that can't be decrypted is left out and named in `unreadable` (never its value), and the controller then keeps the Secret it has. Sent with `Cache-Control: no-store`; logged with the provider and generation only, never audited per call. Decided 2026-10-28 (§5): the server keeps DNS credentials in the row, and the controller holds them only long enough to write the Secret. Served over plain HTTP inside the cluster like every `/internal/dns` route (decided by JP, 2026-10-28; below). |

As implemented in restapi step 3:

- **Authentication** goes through an injected `DnsControllerTokenVerifier` (DI token `"DnsControllerTokenVerifier"`, `verify(token) -> { subject }`), which the server implements against the in-cluster JWKS (signature, issuer, audience, expiry); the route then compares the subject, exactly, with `mail:dns:controller:subject`. No verifier registered, no subject configured, no `Authorization: Bearer` token, an invalid token or another subject are all the same 403. A user's JWT is never accepted.
- **Refusals** are `400 { reason: "unsupported_api_version", supported: [...] }` for another `apiVersion` or `kind`, and `400 { reason: "invalid_payload", message }` for a malformed handshake, status report or `since` (the message names the field, never a value). A status report is validated whole before anything is stored; unknown fields are dropped and messages cut to 2000 characters.
- **`GET` carries its version in the path** (`/v1/...`); a server rolled back to one without `/v1` answers 404, which sends the controller back to the handshake.
- **Long poll:** `DnsPublisher.version()` is read before the rows; while it equals `since` the route waits on `DnsPublisher.waitForChange(since, mail:dns:desired_state:long_poll_seconds * 1000, signal)` (default 55), the signal aborting when the controller goes away. A version **behind** `since` (the counter was reset: Redis restarted without persistence, a rebuilt server) is answered at once, so the controller learns the new count instead of waiting out every poll; the controller must therefore treat any version other than its own as a change, not only a higher one.
- **Only the Lease holder's report acts** (`lease.holder: true`): it alone updates providers, endpoints, operations and `lastReport`. A report from a pod without the Lease (a stuck old pod during a rollout, a new one waiting for the Lease) is answered the same way and recorded only as `lastStandbyReport`, so two reporters can't flip a provider's status back and forth or bump row versions under the admin's edits.
- **Status writes** happen only on change: a provider's `status` when something but `reportedAt` changed, or every 5 minutes otherwise; a domain's `dnsPublication.endpoints` only when the reported endpoint differs; so a report every minute doesn't race the admin's versioned edits. A write that loses a race is logged and the next report carries the same news. Entries naming a config, endpoint set or operation that no longer exists are ignored.
- **List-valued options** (`string[]`: Cloudflare's `zoneIds`, rfc2136's `hosts`) are in both copies of `DnsProviderV1.options` and in the shared desired-state fixture (`zoneIds` as a list, the wire shape every Cloudflare config has), changed in both repositories together. The `StatusReportResult` kind, first only in restapi's copy, is in the controller's since its phase C2.
- **Configuration** the route reads: `mail:dns:controller:subject`, `mail:dns:desired_state:long_poll_seconds`, `mail:dns:publish:ttl` (300; raised to 120 for Cloudflare), `mail:dns:publish:hosts` and `mail:dns:publish:addresses` (lists, or their JSON strings; invalid entries and non-global addresses are logged once and left out), `mail:dns:publish:external_dns_image` (default `registry.k8s.io/external-dns/external-dns:v0.23.0`), `mail:dns:mx_hostname`, `mail:autodiscover:public_url`.
- **Credentials in the desired state** (rework of the `v1` types, 18): `DnsProviderV1.secretRef` (`{ backend, path, keys, generation }`) becomes `credentials?: { keys: string[]; generation: number } | null`. Neither side has released `v1`, so it changes in place, in both copies and the shared fixtures together, rather than as an additive field (decided by JP, 2026-10-28). **As implemented (restapi R2):** restapi's copy and `test/fixtures/dns-api/v1/desired-state.json` have it; the dns-controller's copy and fixtures (with `provider-credentials.json` and `provider-credentials-unreadable.json`) followed in its D2, byte-identical to restapi's (`cmp`). `credentials` is left out of a provider without saved credentials (including one cleared to `null`); `keys` are the saved field names in order, `generation` the row's `credentialsGeneration`.
- **The credentials route, as implemented (restapi R2):** `GET /internal/dns/v1/providers/:uid/credentials` answers `kind: "DnsProviderCredentials"` (`DnsProviderCredentialsV1`, and the fixtures `provider-credentials.json` and `provider-credentials-unreadable.json`, shared with the controller like the others) with `providerUid`, `generation` (0 for a row that never had credentials), `values` and, only when something couldn't be read, `unreadable`: the names of those fields, never why. It reads the row afresh (`skipCache`), decrypts with the injected `ConfigCipher` (`decryptString()`, one field at a time; only a `ConfigSecretUnavailableError` makes a field unreadable, any other failure surfaces), sends `Cache-Control: no-store`, logs one info line with the provider and generation, and warns once per process and field about an unreadable one. 403 for any caller but the controller's token, 404 for a config that is gone, 503 for a config that has credentials on a server that registers no `ConfigCipher`. A config without credentials needs no cipher.
- **Desired-state contents:** every provider config (disabled ones too), one endpoint set per domain published through an existing config covering it (disabled domains too; a set with no publishable record is left out), the hosts' sets without the records a domain's set already publishes (6.3) (each host through the config whose zones cover it most specifically; `address` hosts get A and AAAA records for the global unicast addresses; a `cname` host points at its `target`, else the mail host; a host no config covers, an address host without addresses and a CNAME without a target stay manual), and the operations still `queued` or `running`.

**Plain HTTP inside the cluster (decided by JP, 2026-10-28).** The controller reaches the server's `/internal/dns` routes, the credentials route included, over plain HTTP on the server's in-cluster Service (`DNS_CONTROLLER_SERVER_URL`, `http:`), as postfix-bridge reaches `/internal/mta`; the internal API gets no TLS. It is never reachable from outside: the Gateway answers `/internal` with 404 and the server refuses an `/internal` request that arrived through a proxy (`InternalCallerGuard`), and only the controller's token is accepted. The reasoning, under JP's standing rule that a security measure must address a real threat: the one thing TLS would add is protection from someone observing pod-to-pod traffic, and whoever can do that already has node-level access, and with it the configuration keyring and the database (and the Secret external-dns reads), so encrypting this hop would not stop that attacker.

**No internal API on the controller (decided by JP, 2026-10-28).** The controller's own internal API (C2: its listener on port 8080, its Service, the server's projected token for the audience `rapidmx-dns-controller` verified against `DNS_CONTROLLER_SERVER_SUBJECT`, and the NetworkPolicy admitting the server) was built for the `PUT`/`DELETE /v1/secrets/:path` routes of the Kubernetes-Secret backend. With that backend gone the server calls the controller for nothing, so all of it is removed (18.1); the controller keeps only its health endpoints (7.7). Every call goes from the controller to the server.

As implemented in dns-controller C2 (`src/api/ServerClient.ts`, `src/DesiredStateSync.ts`; as first built also `src/auth/ServiceAccountTokenVerifier.ts` and `src/InternalApiServer.ts`, which the rework deletes):

- **Reading the desired state.** The first request of a run (at start, and after every return to the handshake) has no `since` and is taken as a change whatever its version; every later one passes the version the controller has, and any other version in the answer is a change. Requests start at most once a second, so a server answering at once can't make the poll spin. The client's timeout for a long poll is `DNS_CONTROLLER_LONG_POLL_TIMEOUT_SECONDS` (75), above the server's 55. A failure applying a new state (C3's reconcile) is logged `desired_state_apply_failed` and the poll goes on.
- **A malformed desired state is refused whole** (`parseDesiredState()`), never entry by entry: the controller publishes exactly the desired state, so an endpoint set or provider dropped from it would be deleted from the zone. That includes a provider type, record type or operation the controller doesn't know, which a server can therefore only add in lock-step with the controller. Unknown fields are left out. The last good state stays in use and the request is retried with backoff (1 s doubling to 30 s), logged `desired_state_invalid`.
- **Back to the handshake** on a 404 or `400 unsupported_api_version` from any `/v1` call, or an answer of another `apiVersion` or `kind`: the sync stops, the controller stops writing (the Lease is kept: it is usually a server restart) and handshakes again, at once the first time and then at most once every `DNS_CONTROLLER_HANDSHAKE_RETRY_SECONDS`, so a server answering the handshake "compatible" without serving `/v1` can't make it spin. A 401/403 is logged as the server refusing the controller's token and retried like a server that can't be reached (not a mismatch).
- **Status reports** go out after every new desired-state version and every `DNS_CONTROLLER_STATUS_INTERVAL_SECONDS` (60), never two at once, from the Lease holder and from a pod without the Lease alike (`lease.holder` says which; the server keeps the latter as `lastStandbyReport`). C2 reports the controller itself with empty `providers`, `endpoints` and `operations`; C3 fills them in. **As implemented in dns-controller D3:** only the holder reads and sends the entries (a pod without the Lease sends itself alone), read for the desired state the report names, which the controller captures once per report; a report also goes out when each reconcile pass ends, since the one sent as a state arrives reads the cluster before the pass applied it (the applied generation then shows at once, `observedGeneration` and the Deployment's readiness when the next report reads them). The entries come from two label-selected lists, one of Deployments and one of `DNSEndpoint`s (no new rights, no Secret read); a list that fails leaves its entries out (`status_entries_failed`), and an `entries` read that throws sends the report without them.
- **The health port** listens on `::` (IPv4 too on a dual-stack pod, `0.0.0.0` where the pod has no IPv6), so a single-stack IPv6 cluster reaches it.
- **Removed with the controller's internal API** (decided 2026-10-28, above; 18.1): the listener on `DNS_CONTROLLER_API_PORT` (8080), which took the server's projected token (audience `DNS_CONTROLLER_API_AUDIENCE`, `rapidmx-dns-controller`) with the exact subject `DNS_CONTROLLER_SERVER_SUBJECT` (required, so the controller didn't start without it), answered every failure with the same 403 and served nothing while the controller couldn't write (C2 had no routes on it), and its token verification (`ServiceAccountTokenVerifier`: RS256/ES256 by `kid`, issuer, audience, `exp`/`nbf` with a minute of skew, RSA keys of 2048 bits or more, the JWKS fetched again for an unknown `kid` at most once a minute). The settings `DNS_CONTROLLER_SERVER_SUBJECT`, `DNS_CONTROLLER_API_PORT` and `DNS_CONTROLLER_API_AUDIENCE` go with them.
- **What the chart sets** (server step S9): besides the C1 variables, when not the defaults, `DNS_CONTROLLER_LONG_POLL_TIMEOUT_SECONDS` (keep it above `mail:dns:desired_state:long_poll_seconds`) and `DNS_CONTROLLER_STATUS_INTERVAL_SECONDS`.

**Authentication: projected ServiceAccount tokens, no shared secrets.** The controller presents a projected ServiceAccount token with a dedicated audience, `rapidmx-internal-dns` (1 hour, rotated by the kubelet, re-read from the file on every call). The server verifies the signature against the cluster's service-account issuer keys, the issuer, the audience, the expiry, and the exact subject (`system:serviceaccount:<namespace>:<fullname>-dns-controller`). Keys are cached and refetched on an unknown `kid` (at most once a minute). No TokenReview (it would need a ClusterRole) and no long-lived secret. Nothing authenticates to the controller: it serves no API (as first built, the server also presented a token with the audience `rapidmx-dns-controller` to the controller's internal API, removed above).

- **The keys are fetched in-cluster:** `GET https://kubernetes.default.svc/openid/v1/jwks` (and the issuer from `/.well-known/openid-configuration` on the same host), authenticated with the pod's own ServiceAccount token and verified with the cluster CA. The `jwks_uri` the discovery document advertises is **not** used: on k3s it is the node's public address on port 6443, which a pod may not be able to reach and which the in-cluster certificate name does not cover.
- **Checked on powerlevel.gg's k3s v1.36.4 (2026-10-27):** the default `system:service-account-issuer-discovery` ClusterRoleBinding exists and grants every ServiceAccount (`system:serviceaccounts`) read access to `/openid/v1/jwks` and the discovery document, so neither side needs extra RBAC. On other distributions the installer checks for the binding and reports it missing instead of failing later.

Reconcile triggers on the server side only bump the desired-state version, which ends the controller's long poll:

| Trigger | Scope |
| --- | --- |
| `Domain` create, update (`enabled`, `dmarcPolicy`, `dmarcReportEmail`, `aliasOf`, DKIM fields), delete | that domain |
| `dnsProviderUid` assignment | that domain, old and new provider |
| DKIM key created or backfilled; every DKIM rotation phase change | that domain |
| Autodiscover plugin enabled/disabled, `mail:autodiscover:public_url` change | all domains |
| `DnsProvider` create, update, credentials change (a new `credentialsGeneration`), enable/disable, delete | that provider |
| Takeover or test requested | queued operation |

restapi raises these through an injected `DnsPublisher` (DI token, `NullDnsPublisher` by default, so restapi alone and a non-Kubernetes deployment behave as today); the server's implementation bumps the version (a counter in Redis, so every replica answers long polls consistently). The controller also does a full reconcile on start and every 10 minutes (`dns.controller.resyncMinutes`).

As implemented: `DnsPublisher` has `changed(change)`, `version()` and `waitForChange(since, timeoutMs, signal?)`; a change is `{ scope: "domain" | "provider" | "operation" | "all", ... }`. Every caller has already saved its change, so `notifyDnsPublisher()` logs a failure instead of failing the request. The routes resolve the publisher tolerantly (`resolveDnsPublisher()`): a server that registers none gets `NullDnsPublisher` with a warning instead of failing to boot. The domain route announces a create, a delete, an update that changes `enabled`, `dmarcPolicy`, `dmarcReportEmail`, `aliasOf` or the DKIM fields, an assignment, a DKIM backfill and every apex TXT change; the provider route every create, update and delete, and every queued operation. The Autodiscover plugin being enabled or disabled is picked up by the controller's periodic resync until the server announces it (server step 4).

### 7.4 The external-dns Deployment

- Created by the controller per provider config: name `<fullname>-external-dns-<provider uid>`; labels `app.kubernetes.io/name: external-dns`, `app.kubernetes.io/instance: <release>`, `app.kubernetes.io/managed-by: rapidmx-dns-controller`, `rapidmx.io/dns-provider: <provider uid>`.
- **Image pinned**: `registry.k8s.io/external-dns/external-dns:v0.23.0` (released 2026-09-18; tag confirmed on registry.k8s.io), pulled by digest, from `dns.externalDns.image`. The controller refuses any other image than the configured pin. v0.24.0 adds admission validation of `DNSEndpoint` and is not adopted now; moving to it means re-applying the CRD.
- `replicas: 1` (0 when the provider config is disabled), `strategy: Recreate`: external-dns has no leader election, and two instances with one owner id would fight.
- ServiceAccount `<fullname>-external-dns` (created by the chart, shared by all instances), bound to a Role allowing only `get`/`list`/`watch` on `dnsendpoints` and `update` on `dnsendpoints/status`. This matches external-dns's own chart with `namespaced: true`; a crd-only source needs no `nodes` or `namespaces` access.
- Probes on `/healthz`, port 7979. Hardened like the controller.
- Arguments:

```
--source=crd
--crd-source-apiversion=externaldns.k8s.io/v1alpha1
--crd-source-kind=DNSEndpoint
--namespace=<release namespace>
--label-filter=rapidmx.io/dns-provider=<provider uid>
--provider=<type>
--domain-filter=<zone>            (one per DnsProvider.zones entry)
--registry=txt
--txt-owner-id=rapidmx-<installationId>
--txt-prefix=rmx-%{record_type}.
--managed-record-types=A --managed-record-types=AAAA --managed-record-types=CNAME
--managed-record-types=MX --managed-record-types=TXT --managed-record-types=SRV
--policy=sync
--interval=1m
--events
--log-format=json
--metrics-address=:7979
<provider-specific flags from DnsProvider.options>
```

- `--policy` has no default since v0.22.0. `--managed-record-types` defaults to A, AAAA and CNAME, so MX, TXT and SRV are listed (MX and SRV are left out for rfc2136).
- `--txt-owner-id` is per deployment (`DeploymentIdentity.installationId`, 4.6), so two deployments sharing a zone never claim each other's records. It never changes.
- `--txt-prefix` with `%{record_type}` and a trailing `.` is required: without it the ownership record for an apex record (`mx-example.com`) falls outside the zone, and the registry's TXT cannot sit next to a CNAME. The MX at `example.com` is owned by a TXT at `rmx-mx.example.com`. The prefix never changes.
- Credentials come only from the Secret (env `valueFrom.secretKeyRef` or a mounted file), never as arguments. The Secret is a derived copy, the one external-dns needs because it reads credentials no other way: the controller writes it from the credentials the server sends (7.3) and nothing else writes it (decided 2026-10-28, §5; no `ExternalSecret` path for DNS credentials).

As implemented in dns-controller C3 (`src/reconcile/manifests.ts`, `src/reconcile/Reconciler.ts`):

- **The arguments** are exactly the list above, in that order, followed by the provider's: Cloudflare `--zone-id-filter` per id; Route 53 (`--provider=aws`) `--aws-zone-type` and `--aws-assume-role`, with `AWS_REGION` from `region` as a plain variable; rfc2136 `--rfc2136-host` per server, `--rfc2136-port`, `--rfc2136-zone`, `--rfc2136-tsig-keyname`, `--rfc2136-tsig-secret-alg`, `--rfc2136-insecure` when set, and `--rfc2136-axfr`; Google `--google-project`; Azure `--azure-config-file=/etc/external-dns/azure/azure.json`, `--azure-subscription-id`, `--azure-resource-group`. An option of the wrong shape, or one the controller doesn't know, is left out. `--cloudflare-proxied` is never passed (its default is off).
- **Nested zones** (added on review): every instance shares the owner id and runs `--policy=sync`, so an instance whose `--domain-filter` (a suffix match) covers another config's zone would take that config's records for its own and delete them on every sync, wherever both reach the same provider zone (one Cloudflare zone, or two Route 53 hosted zones in one account). A zone of another config (enabled or not) under one of this config's zones is therefore passed as `--exclude-domains=<zone>`, right after the `--domain-filter`s (`nestedZones()`; v0.23.0's `DomainFilter.Match` applies the exclusion to zones and to the plan's records). A domain under such a nested zone is then published only by the nested config: **restapi assigns a domain only to the most specific config covering it** (as it already chooses for the hosts; implemented in R2, 10.4), or a domain assigned to the parent stays pending. The same zone in two configs can't be separated and is refused (below); **restapi refuses it too** (409 on create and update, implemented in R2, 10.1), so the admin learns it there rather than from a stalled controller.
- **The credentials Secret** is `<fullname>-dns-<provider uid>`, its keys the credential field names (`apiToken`, `accessKeyId`/`secretAccessKey`, `tsigSecret`, `serviceAccountJson`), read as `CF_API_TOKEN`, `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` (only when both are saved; neither is IRSA), `EXTERNAL_DNS_RFC2136_TSIG_SECRET`, or Google's key mounted as `/etc/external-dns/google/credentials.json` with `GOOGLE_APPLICATION_CREDENTIALS`. **Azure** reads one file whose tenant isn't a flag, so its Secret holds `azure.json` (`tenantId`, `aadClientId`, `aadClientSecret`): the controller builds it with `JSON.stringify` from the tenant in the provider's options (refused unless exactly a GUID) and the fetched client id and secret. (As first built, the `ExternalSecret`'s template built it; that goes with the `ExternalSecret`.)
- **A config whose saved credentials lack a required field** (Cloudflare's `apiToken`, Google's key, Azure's client id and secret, rfc2136's TSIG secret unless `insecure`) runs with `replicas: 0`, as a disabled one does, instead of crash-looping.
- **Writing the Secret (rework of C3, 18; as implemented in D2):** on each pass the controller reads the Secret's metadata only (`PartialObjectMetadata`); when it is missing, or its `rapidmx.io/credentials-generation` annotation isn't the config's `credentialsGeneration` (or is gone or not a number), or none of the Deployment owners in its `ownerReferences` has the uid of the Deployment just applied (a Deployment deleted and recreated by hand gets a new uid, and the garbage collector would take the Secret with the old one), it fetches the credentials (`GET /internal/dns/v1/providers/:uid/credentials`, only while it may write, asked at the moment of the fetch) and applies the Secret with the values, the annotation and the labels `app.kubernetes.io/managed-by: rapidmx-dns-controller`, `app.kubernetes.io/instance`, `rapidmx.io/dns-provider` and `rapidmx.io/secret-kind: dns`, with an `ownerReference` to the provider's Deployment (its `apiVersion`, `kind`, `name` and `uid`; not `blockOwnerDeletion` or `controller`, which would need a right on the Deployment's finalizers). The Deployment is therefore applied first, its answer carrying the uid, and when the Secret held an older generation it is applied again once the Secret holds the new one, which is what rolls the pod; until then the pod template carries the generation the Secret held, or `-1` for a Secret whose generation is unknown, so that the pod rolls after the rewrite and not before. The answer must be about that provider and at exactly the generation the desired state lists (any other, older or newer, writes nothing and is tried again on the next pass; the next desired state carries the right one), and must have every field the state lists: a field the server names in `unreadable`, or one the answer lacks, keeps the Secret as it is (`credentials_unreadable`, naming fields only). The Secret holds the fields the provider type reads by name (Azure's holds only `azure.json`); any other field is left out. A Secret of that name that lacks this controller's labels (`managed-by`, `secret-kind: dns` and the provider) is never written over or run an instance on: that config fails (`reconcile_failed`) and its Deployment is not applied. The values live in the controller's memory only for that write and are never logged. A config without credentials gets no Secret (one the controller wrote is deleted, and only once the Deployment was applied without the references to it, so never while the image is refused: `secret_delete_deferred`; a foreign one is left alone), and a disabled config's Secret is written like any other. A fetch that fails (`credentials_fetch_failed`; the server's 404 for a config that is gone is also what a server without the route answers, so it is no more than a failed fetch here, and the desired-state poll is what finds a rolled-back server) leaves the Secret as it is and retries with the pass's backoff.
- **As first built** (`4bde52b`), with OpenBao the controller applied an `ExternalSecret` of the same name (`refreshInterval: 1h`, the release's `SecretStore`, `remoteRef.key` `<integrations prefix>/<SecretRef.path>`), and External Secrets wrote the Secret; the rework removes it, its settings and its pruning. No `ExternalSecret` of it was ever deployed (the server chart never templated the controller), so there is nothing to clean up, and the controller's Role loses `externalsecrets` (7.6).
- **Rolling on new credentials:** the Deployment's pod template carries **the generation the Secret already holds**, read as metadata only, so the pod rolls once the new credentials are there rather than restarting with the old ones; while the Secret is behind, the pass is retried. A Secret not there yet counts as the config's generation.
- **The image pin:** every Deployment runs the configured `DNS_CONTROLLER_EXTERNAL_DNS_IMAGE` (the chart's `dns.externalDns.image`, by digest). The desired state's `externalDnsImage` must be that reference or, when the pin adds `@sha256:...`, its tag alone (the server's default has no digest); any other leaves every Deployment as it is (`external_dns_image_refused`), while the `DNSEndpoint`s are still applied, and so is a Secret that is behind when an instance exists to own it (without one it waits, `credentials_deferred`).
- **Applying:** server-side apply as `rapidmx-dns-controller` with `force` (fields edited by hand are taken back), the gate (compatible and holding the Lease) asked immediately before every write. A state with a malformed or repeated provider uid or endpoint set id, a set naming a provider the state doesn't have, a provider without zones (it would run with no `--domain-filter`, on every zone its credentials reach) or with a zone that isn't a lowercase domain name of two or more labels, a zone listed by two configs, or credentials whose field names aren't letters, digits, `-` and `_` (as first built: a `secretRef` path outside `dns/`), is refused whole before any call (`desired_state_unpublishable`), like `parseDesiredState()`. One object that fails is logged (`reconcile_failed`) and the others are still written.
- **Pruning** lists what this release's controller manages (`app.kubernetes.io/managed-by=rapidmx-dns-controller,app.kubernetes.io/instance=<release>`): a `DNSEndpoint` the state no longer has is deleted. A **deleted provider** (an instance labelled for a uid the state no longer has) keeps its Deployment for 2 minutes after its endpoints were deleted (one interval and a margin, in memory: a restart waits again), then the Secret and last the Deployment are deleted, the Secret only when its labels name this controller, `secret-kind: dns` and that provider. The Deployment goes last because it is the only object that marks the provider as deleted (Secrets are never listed): a failure leaves it for the next pass. A Secret whose Deployment is gone otherwise (deleted by hand) goes with it through its `ownerReference`. Nothing of it is removed while one of its endpoints couldn't be deleted, or while any list failed. A provider that comes back before then starts over.
- **Status entries (D3):** per provider the ready replicas of its Deployment (0 when it is missing, has no status, or its `observedGeneration` is behind its generation), the image of its `external-dns` container and `lastRolloutAt`; per endpoint set the `DNSEndpoint`'s `metadata.generation` and, once external-dns has read it, `status.observedGeneration` (a set whose `DNSEndpoint` isn't there is left out); per operation the result the controller holds for each operation the desired state lists. `lastError`, `lastSyncAt` and the metrics are D5's. The results are kept in memory (`OperationLedger`), pruned as a desired state arrives and cleared when the Lease is lost; D4 records a result only for an operation of the latest state.
- **When:** on every new desired state, at once when the controller takes the Lease, every `DNS_CONTROLLER_RESYNC_MINUTES` (10, the chart's `dns.controller.resyncMinutes`), when a deleted provider's removal is due, and after a pass left something undone, with backoff from 15 s to a minute. Passes never overlap. On shutdown no further write starts, and the Lease is released only once the request under way has been answered, so it can't land after a successor took the Lease.
- **Configuration** the chart sets (server step S9): `DNS_CONTROLLER_FULLNAME` and `DNS_CONTROLLER_RELEASE` (required), `DNS_CONTROLLER_EXTERNAL_DNS_IMAGE`, `DNS_CONTROLLER_EXTERNAL_DNS_SERVICE_ACCOUNT` (default `<fullname>-external-dns`), `DNS_CONTROLLER_EXTERNAL_DNS_RESOURCES` (JSON), `DNS_CONTROLLER_RESYNC_MINUTES`. As first built also, with OpenBao, `DNS_CONTROLLER_OPENBAO_SECRET_STORE`, `DNS_CONTROLLER_OPENBAO_PATH_PREFIX` and `DNS_CONTROLLER_EXTERNAL_SECRETS_API_VERSION`, which the rework removes.

### 7.5 `DNSEndpoint` resources

- One `DNSEndpoint` per domain (`<fullname>-domain-<domain uid with dots as hyphens>`) holding all of its records, and one for the hosts (`<fullname>-hosts-<provider uid>`). The desired state names them by endpoint set id (`domain-example-com`, `hosts-<provider uid>`), which the controller prefixes. A domain name with a hyphen of its own gets an 8-character hash of the name appended (`a-b.example.com` and `a.b-example.com` would otherwise share an id), and so does one over 180 characters (cut first).
- Labels: `rapidmx.io/dns-provider: <provider uid>` (what `--label-filter` selects), `rapidmx.io/domain: <domain uid>`, `app.kubernetes.io/managed-by: rapidmx-dns-controller`, `app.kubernetes.io/instance: <release>`.
- Reassigning a domain to another provider rewrites the label: the old instance deletes the records it owns (sync policy), the new one creates them. The console warns that this briefly removes them.
- `spec.endpoints[]`: `dnsName`, `recordType`, `targets` (TXT targets quoted, 4.2), `recordTTL` (`mail:dns:publish:ttl`, default 300; Cloudflare needs at least 120), and `providerSpecific` only where needed (Cloudflare `cloudflare/proxied: "false"` on A/AAAA/CNAME). The registry's own ownership TXT records carry no TTL (9.3).
- Writes use server-side apply (`fieldManager=rapidmx-dns-controller`), so every write is idempotent. The controller's own Kubernetes client (in its repository, 7.2) has `GET`, `POST`, `PUT`, apply `PATCH` and `DELETE`; the server's `KubeClient` stays GET-only.
- `status.observedGeneration` is written by external-dns when it **reads** the resource, not when the provider has applied it. "Published" therefore means observed **and** seen by the server's live check. Observed but not live is "pending"; still not live after several intervals is shown with the instance's last error.

As implemented in dns-controller C3: Cloudflare's property is `cloudflare/proxied` (`annotations.CloudflareProxiedProperty` in v0.23.0), on A, AAAA and CNAME only; `recordTTL` is set only when the server sends a TTL; a kind the provider can't keep (rfc2136's MX and SRV) is left out of the endpoint even if sent, and so is a TXT record it can't keep (4.2); TXT targets take each provider's form (quoted for Cloudflare, Route 53 and Google, verbatim for Azure, unquoted plain values for rfc2136); `rapidmx.io/domain` is left off for a domain name longer than a label value (63 characters), since nothing selects by it. `ownershipEndpoint()` builds the registry's ownership record (no TTL) for the C4 Jobs; the regular endpoints never carry one.

Deletion: a deleted domain's endpoint is deleted; external-dns removes what it owns on its next sync, and a managed apex TXT set is restored afterwards (9.5). A provider config can be deleted only when no domain is assigned to it and no `restore` operation of it is queued or running (409 otherwise: a restore runs only with that config's credentials, so deleting it first would lose the kept values); its other queued or running operations are cancelled (4.8). The server removes the row, and the encrypted credentials with it (the running instance keeps the copy in its Secret until the controller deletes it); the controller then deletes its hosts endpoint, waits one interval, and deletes the Secret and the Deployment.

### 7.6 RBAC

The server's Role is unchanged (read-only Diagnostics access). Its only write right anywhere is, without OpenBao, the separate Role `<fullname>-config-keyring`: `get` and `update` on the one keyring Secret by `resourceNames`, for rotating the configuration key (5.5; approved by JP, 2026-10-28); with OpenBao it has none, and writes the keyring's KV path instead. The server is read-only on every other Kubernetes resource. The controller's Role `<fullname>-dns-controller`, in the release namespace only:

| apiGroups | resources | verbs |
| --- | --- | --- |
| `apps` | `deployments` | get, list, watch, create, update, patch, delete |
| `""` | `secrets` | get, create, update, patch, delete; the per-provider Secrets (`<fullname>-dns-<uid>`, names not fixed, so no `resourceNames`) are checked by label before any change |

Plus the external-dns Role (7.4). No ClusterRole anywhere. As first built, the controller's Role also had `externalsecrets` (with OpenBao) and a `resourceNames` rule for `<fullname>-integration-secrets`; the rework removes both (18).

As implemented in dns-controller C3, the controller **reads the per-provider Secrets' metadata** (`get` on `secrets`, as `PartialObjectMetadata`: the generation their credentials are at, and the labels checked before changing or deleting one), whose names aren't fixed, so that `get` can't be limited by `resourceNames`; it never reads a Secret's data (it has the values from the server when it writes). Kept after review: the Role's right to create Deployments and Jobs already lets it read any Secret of the namespace by mounting it, so the broad `get` adds no capability; the controller only ever reads names built from a validated provider uid. It lists `deployments` and `dnsendpoints` by label (and, as first built, `externalsecrets`).

### 7.7 Health and status

The controller scrapes each external-dns pod's `/metrics` (pod IP, port 7979) every interval, and reports per provider:

- Deployment: ready replicas, image, last rollout. As implemented in D3, `lastRolloutAt` is the last update of the Deployment's `Progressing` condition, reported only when it is `True` with reason `NewReplicaSetAvailable` (a completed rollout): the Deployment controller also moves that time during a rollout and when one fails (`ProgressDeadlineExceeded`), so those leave it out. It is an additive optional field of `ProviderStatusV1`, not in the shared `status-report.json` fixture yet.
- From metrics: time of the last successful sync, registry, source and provider error counters, and `external_dns_registry_skipped_records_owner_mismatch_per_sync` (conflicts). The exact metric names are taken from v0.23.0 and covered by a test against a recorded `/metrics` page.
- Per endpoint: `observedGeneration`.

The server stores the report on `DnsProvider.status` and `Domain.dnsPublication`; the console reads it from the server. Diagnostics lists the controller and each external-dns pod with the other containers (through its existing read access).

## 9. Takeover of Existing Records

### 9.1 The problem

external-dns's TXT registry only changes records it owns, and it has no adopt flag or annotation (`--migrate-from-txt-owner` only moves records between two of its own owner ids). Its planner (`plan.go`, v0.23.0):

- Updates and deletes of records with another owner, or none, are silently filtered out.
- **Creates are skipped for the whole name** when any existing record of a managed type at that name is not owned. An unowned SPF TXT at the apex therefore also blocks the creation of the MX at the apex. The skip is logged at debug level only; a metric counts it.
- A TXT value that is not an ownership record is never deleted.

### 9.2 Rule

Takeover is **opt-in per provider config** (`allowTakeover`, default false; installer flag `--dns-takeover`) and only for names this deployment wants to publish. Without it, a conflicting record's state is `conflict`, and the console shows the existing value next to the wanted one with a "Take over" action for that domain (trusted role and elevation, audited `DNS_TAKEOVER`).

The apex TXT set is never taken over by `allowTakeover` alone: it needs the per-domain opt-in of 9.4.

### 9.3 Mechanism (proven on Cloudflare, 2026-10-27)

1. **Detection (server).** For each desired name, the server resolves the current records of every managed kind and the ownership TXT (`rmx-<type>.<name>`). A record present without this deployment's ownership value is a conflict.
2. **Apply (controller).** The controller runs a one-shot `Job` from the pinned image with the provider's credentials and arguments, `--registry=noop --policy=upsert-only --once`, a dedicated label filter, and a temporary `DNSEndpoint` holding the desired records **plus the ownership TXT records the TXT registry would have written**. With the noop registry, external-dns treats every record as its own and upserts it.
3. The Job and the temporary endpoint are deleted. The regular instance (`--registry=txt --policy=sync`) now sees the records as owned and manages them from then on.
4. The same Job creates a record at a name where creation is blocked by an unowned record of **another** type (9.1: the MX at an apex whose TXT set RapidMX does not manage). It only creates the wanted record and its ownership TXT; the unowned set is not touched. This is needed **only for the first creation**: once the MX and its ownership record exist, the regular instance updates and deletes it (checked live, 2026-10-28, below).

**Spike results** (hand-run on powerlevel.gg against Cloudflare with external-dns v0.23.0, JP's scoped token, 2026-10-27):

- **The noop-registry takeover works.** The one-shot `--registry=noop --policy=upsert-only --once` Job overwrote the hand-made, unowned records, and afterwards a `--registry=txt --policy=sync` instance with the same owner id treated them as its own (updates and deletes applied). The fallback (a per-provider delete call) is not needed.
- **Ownership record format**, which the Job must write exactly: name `rmx-<lowercase record type>.<record name>` (for example `rmx-mx.powerlevel.gg`, `rmx-cname.openpgpkey.powerlevel.gg`); value, including the surrounding double quotes, `"heritage=external-dns,external-dns/owner=rapidmx-<installationId>,external-dns/resource=crd/<namespace>/<regular DNSEndpoint name>"`. The `resource` must name the **regular** endpoint, not the temporary one, so the regular instance does not see a resource change.
- **No TTL on ownership TXT records.** The registry writes them without `recordTTL` (the provider's default/automatic TTL); the Job's ownership endpoints carry none either, so the regular instance finds nothing to update. Only the wanted records carry `mail:dns:publish:ttl`.
- **TXT targets must be quoted** (4.2): the wanted TXT records in both the temporary and the regular endpoint are written as `"\"...\""`; unquoted targets differ from what the provider returns and are rewritten on every sync.
- **After a takeover the whole set is owned.** external-dns manages a name and type as one set: a value added at the provider by hand afterwards is **removed** on the next sync, and deleting the endpoint removes **every** value of the set, including foreign values that were deliberately carried over. This is what drives 6.5 (ownership verification off the apex), 9.4 (the apex TXT only on opt-in, edited only in the console) and 9.5 (restoring kept values).
- **An unowned record at a name blocks only creation there** (checked live on powerlevel.gg against Cloudflare with external-dns v0.23.0, 2026-10-28, every test record removed afterwards): with an unowned TXT set at the apex, the regular `--registry=txt --policy=sync` instance updated and deleted an MX it already owned at the same name, and only the creation of a new MX there was skipped. So the one-shot Job of step 4 is needed only for the MX's first creation at an unmanaged apex, never for a later change, and the controller treats an MX that is owned and present as any other record.

The ownership-record format is re-checked against `registry/txt` and `registry/mapper`, and the spike re-run, whenever the external-dns pin moves.

**As implemented in dns-controller C4** (`src/reconcile/OperationRunner.ts`; `operationJob()` and `operationEndpoint()` in `manifests.ts`):

- **When:** at the end of every reconcile pass that published the desired state, after the endpoints are applied and pruned, and not while the image pin refuses the state (`external_dns_image_refused`). Only the Lease holder runs them (every write asks the gate first). A pass with an operation not yet finished ends `incomplete` (retried from 15 s; a waiting restore also sets the time it is due), and a report follows each pass, so the server sees `running` and then the result.
- **The Job** `<fullname>-op-<first 16 hex of the sha256 of the operation id>` (the id is any text, so it is hashed for names and label values and kept whole in the annotation `rapidmx.io/dns-operation-id`; a long release name is cut so the name stays at most 63 characters): the pinned image, the provider's credentials by reference (the same wiring as its instance), the instances' ServiceAccount and the same hardening, `--source=crd` with `--label-filter=rapidmx.io/dns-operation=<hash>`, the provider's `--domain-filter`s and nested-zone `--exclude-domains`, `--registry=noop --policy=upsert-only`, the provider's `--managed-record-types`, `--once` (and `--dry-run` for a test), `--log-format=json` and the provider's own flags. No `--txt-owner-id`, `--txt-prefix`, `--interval` or `--events` (nothing is registered, and the instances' ServiceAccount can't create events). Its pod carries `app.kubernetes.io/name: external-dns-operation` and no `rapidmx.io/dns-provider` label, so no instance's Deployment selects it. `backoffLimit: 0`, `activeDeadlineSeconds: 300`, no `ttlSecondsAfterFinished` (the Job is the record of the result until the controller deletes it; a TTL could drop a result the server had not yet taken and run the operation again), `terminationMessagePolicy: FallbackToLogsOnError`. It is **created with POST**, never applied: the Role has `create`, `get`, `list` and `delete` on Jobs, not `patch` (7.6), and it is deleted with `propagationPolicy=Background` (a Job deleted through the API otherwise orphans its pods).
- **The temporary endpoint** (takeover and restore; a test has none) has the same name, is labelled `managed-by`, `instance` and `rapidmx.io/dns-operation` (not the provider label, so no instance reads it, and pruning leaves it to the runner), and holds the operation's records in the provider's form exactly as the regular endpoint would (`endpointEntries()`: TXT in its form, TTL, Cloudflare unproxied; what the provider can't keep is left out, and an operation with nothing left fails), then for a takeover one ownership record per name and type (`ownershipEndpoint()`: `rmx-<type>.<name>`, naming the regular endpoint of the operation's `endpointSetId`, no TTL). A restore has none.
- **A takeover waits for the regular endpoint:** it starts only once the regular `DNSEndpoint` holds each name and type it writes. The regular instance deletes what it finds owned and no longer wanted, so owning a record the regular endpoint lacks would delete it. The endpoint is written first, then the Job. A takeover whose names and types the desired state's own endpoint set no longer holds (the domain opted out meanwhile) fails at once, since the regular endpoint would never get them; an operation the newest state no longer lists is not started.
- **A restore waits for the regular instance to remove the set** (9.5, step 1): the regular `DNSEndpoint` no longer holds the name and type (or is gone, as for a deleted domain), the instance has read that generation of the endpoint (its `status.observedGeneration` reached `metadata.generation`; external-dns writes it as it reads the resource), the instance's Deployment has a ready replica of its current spec, and 2 minutes (one interval and a margin, in memory; a restart counts again) have passed since the controller first saw both. Seeing the set back, the endpoint unread or the instance not ready, or losing the Lease (the count is in memory), starts the count again; a disabled provider's restore therefore waits until it is enabled. The controller doesn't read the provider's records, so this is the same wait as for a deleted provider's instance; a ready replica and a read generation don't prove a sync has succeeded (D5's `lastSyncAt` will replace the delay), so the live lookup that confirms the restored set is the server's (9.5, step 3) and is not optional.
- **Every operation waits for the provider's credentials Secret** (present, this controller's labels, at the generation the state lists; none for a config without credentials), reported `running` with what it waits for. A test runs against a disabled config too.
- **Results:** `running` (with the step), then `succeeded` or `failed` from the Job's `Complete` or `Failed` condition. The failure message is the last error external-dns logged (its JSON `level`/`msg`, from the pod's termination message; one list of the Job's pods, `get`/`list` on pods as 7.6 lists), else how the container ended (its terminated reason and exit code, such as `OOMKilled`) or why it never started (the waiting reason), else the Job's own condition reason and message; cut to 500 characters. A log line that is not an error entry is never the reason. It is the provider's error text, which does not echo a credential. An operation that can never run fails at once: its provider config isn't in the state or can't run (a missing required credential), a takeover or restore without an `endpointSetId` (which must be a valid set id, since it becomes part of an object name) or without records, a takeover whose set isn't published through this provider, or nothing the provider can keep.
- **The Job is the record of the result:** it stays until the server stops listing the operation, so a controller that restarts or takes the Lease again (the ledger is then empty) reads the result from the Job instead of running the operation again. The temporary endpoint is deleted as soon as its Job is finished (or when no Job uses it), and both when the operation is no longer listed. The temporary endpoint also outlives a Job creation whose answer was lost (a timeout): the Job may exist and must find it. A result is recorded only while the controller may write and the newest desired state still lists the operation.

### 9.4 The apex TXT set and SPF (DECIDED)

**Decided by JP (2026-10-27):** the root TXT set is never overwritten without the admin's per-domain opt-in, as proposed below.

Because owning a set means owning every value in it (9.3), RapidMX does **not** publish anything into a domain's apex TXT set unless an admin opts that domain in:

- **Default: not managed.** The SPF record is shown in the DNS checklist as manual (`manualReason: "apex_txt_unmanaged"`), exactly as today, with the recommended value. Ownership verification is unaffected (6.5). The MX at the apex is still published (9.3, step 4).
- **Opt-in per domain** (`PUT mail/domains/:id/apex-txt` with `{ managed: true, keep: string[] }`; trusted role and elevation; audited `DNS_TAKEOVER` with the old values): the console first shows every value currently at the apex and pre-fills an **editable "values to keep" list** with all of them except SPF records and `rapidmx-domain-verification=` values (`GET mail/domains/:id/apex-txt`, trusted role: `{ managed, keep, spf?, current, suggestedKeep }`). The admin removes what should go and adds what should be there. RapidMX then owns the set: it publishes `v=spf1 mx ~all` (or the existing SPF verbatim when it already includes `mx`; an SPF without `mx` is replaced, the old value in the audit entry) plus every value on `keep`, through the Job of 9.3 the first time (a queued `takeover` operation) and the regular instance afterwards. The chosen SPF is stored as `apexTxt.spf`.
- **As implemented (restapi step 3):** opting in needs the domain assigned to a provider config covering it (400 otherwise), and the apex looked up: a lookup that can't be answered (a timeout, SERVFAIL, anything but NXDOMAIN or NODATA) is a **503**, since an apex wrongly taken for empty would have every value deleted; `GET` then answers `lookupFailed: true` with empty `current` and `suggestedKeep`, and the console must not offer the opt-in on them. An existing SPF is kept verbatim only when it authorizes the domain's own MX hosts: a bare `mx` or `+mx`, optionally with CIDR lengths (`mx/24`, `mx//64`); `-mx`, `~mx`, `?mx` and `mx:<other domain>` don't, so such a record is replaced. `keep` takes at most 50 values of 1 to 2048 characters without control characters, trimmed and each once; an SPF record in it is a 400 (a name holds one SPF, and RapidMX publishes it), a `rapidmx-domain-verification=` value is dropped. Reassigning a managed domain to another provider or to manual is refused (409) until it opts out, since the provider owning the set must restore the kept values first. Deleting a managed domain queues the same restore as an opt-out. The restore is queued **before** the opt-out's save or the domain's deletion, and cancelled if that write then fails, so the set is never released without it. Deleting a domain assigned to a provider config, or with a managed apex set, needs an elevated token like the opt-out and the assignment (it removes the domain's public records); deleting a manual domain doesn't. `apexTxt` and `dkimRotation` are server-managed: a plain `PUT` drops them, `PUT /:id/apexTxt` is a 403, a create strips them.
- **While managed, the console is the only place to edit the apex TXT values.** It says so prominently ("Values added at your DNS host are removed within a minute; add them here"), and `keep` is editable (same elevation and audit) at any time; each edit bumps the desired-state version.
- **Opting out** (`managed: false`) or deleting the domain restores the SPF value RapidMX published there and the kept values (9.5) when the set is released. The SPF value is restored too: releasing the set deletes all of it, and a domain left without SPF fails SPF, and with a strict DMARC policy DMARC, at every receiver. The admin edits the restored values by hand from then on.
- `Domain.apexTxt` replaces the earlier `dnsPublication.preservedTxt` design, which preserved foreign values silently; this makes them visible and editable instead.

### 9.5 Uninstall and restoring kept values

Deleting a `DNSEndpoint` makes external-dns delete every value of each set it owns (9.3), so a set RapidMX took over is restored, not just deleted. For each managed apex TXT set (opt-out, domain deletion, uninstall):

1. The domain's endpoint (or the apex TXT entry in it) is removed and the controller waits until the regular instance has synced: the set and its ownership record `rmx-txt.<domain>` are gone.
2. The controller runs the one-shot noop Job (`--registry=noop --policy=upsert-only --once`) with a temporary endpoint holding **only the SPF value RapidMX published (`apexTxt.spf`) and the kept values**, quoted, and **no ownership record**, so the restored set is unowned again, as it was before RapidMX, and the domain keeps a working SPF record. The restore operation carries exactly these values.
3. The status report confirms the restored set with a live lookup; a failure is shown in the console and logged, with the values to re-add by hand.

The apex TXT set is absent for up to one sync interval plus the Job's run between steps 1 and 2; the console and the installer say so.

`single_node_install.sh --uninstall` removes only RapidMX's values:

1. Every managed apex TXT set is restored as above.
2. Every `DNSEndpoint` of the release is deleted; the installer waits (bounded) until each external-dns instance has synced, checking the live DNS for the hosts' records.
3. The release is removed.

`--keep-dns` skips all of this.

## 10. Integrations API (restapi, mounted by the server)

All routes: `@RequiresTrustedRole()` plus `assertAdminScope()` (elevation) for every write; reads are trusted role. Every write is audited (4.7) with keys, never secret values.

### 10.1 `system/dns-providers`

| Route | Behaviour |
| --- | --- |
| `GET /` | List (by name), with `status` and `domainCount` (the domains assigned). Credentials appear only as `credentials: { <key>: { "secret": true } }` per key saved (`maskCredentials()`); the envelopes themselves are never returned. `GET /:id` returns one the same way. |
| `GET /types` | The provider types, their option schemas, secret fields and `tested` flag (drives the console form). |
| `POST /` | Create. Body: `name`, `type`, `zones`, `options`, `credentials` (write-only), `enabled`, `allowTakeover`. Validates the type schema; zones must be valid host names of at least two labels (a top-level domain alone is refused); the uid is generated from the name (a slug of at most 31 characters, `dns-` in front when it doesn't start with a letter, then a hyphen and 8 random characters); `origin: "console"`; credentials encrypted (5.2) and saved with the row in its one write, `credentialsGeneration` 1 when any were sent. |

Narrowing `zones` is refused (409) while an assigned domain falls outside them. A `version` other than the row's is a 409 (`INVALID_OBJECT_VERSION`, the same code as the optimistic lock's own failure) before anything is written; the change is one versioned row write, so a write that loses a race is the same 409 and changes nothing. (As first built, with the credentials in a separate store whose write couldn't be undone, a lost race pointed the row at the new `secretRef` and audited `rowWriteFailed`; the rework deletes that handling, 18.) Names are unique through `nameKey`'s index (409 `IDENTIFIER_EXISTS`). Assigned domains are counted and checked across every page, not only the first. A request that changes nothing writes and audits nothing. |
| `POST /:id/test` | Queues a test operation: the controller runs a short `--dry-run --once` Job and reports whether it authenticated and found the zones. Trusted role and elevation; audited `DNS_PROVIDER_TEST`. Answers the queued operation. |
| `POST /:id/takeover` | Body: `domainUid`, optional `records` (record types, all the domain publishes through this config when left out); queues 9.3 with the records exactly as the desired state publishes them. The domain must be assigned to this config (400 otherwise); a record type it doesn't publish, or none publishable (rfc2136's MX), is a 400. | `GET /:id/operations` | The config's latest 50 operations, newest first, with their state and the controller's message. Trusted role. |

As implemented (restapi R2, `BaseDnsProviderRoute`):

- **One row write.** A create saves the row with its envelopes and `credentialsGeneration` 1; an update saves the change, the envelopes and the bumped generation in one version-checked write, so a write that loses a race is the 409 `INVALID_OBJECT_VERSION` and changes nothing, with nothing to undo, audit or announce. Each value is sealed (`ConfigCipher.encrypt()`, associated data `DnsProvider`, the row's `uid`, `credentials.<field>`) before anything is written, so a server without a keyring (or without a registered cipher) answers 503 and changes nothing; clearing credentials needs no cipher. A field sent again with the same value counts as a change (it can't be compared with the envelope without decrypting): it bumps the generation and the controller rewrites its Secret with the same value. Every field cleared leaves `credentials: null`.
- **Re-encryption** of the envelopes by the key rotation (5.5) is the `DnsProvider` envelope source (`dnsProviderEnvelopeSource()`, registered by `ConfigKeyRotationJobMongo`/`SQL`): it saves only `credentials`, never `credentialsGeneration`, since the plaintext, and so the controller's Secret, is unchanged.
- **A new zone can't take an assigned domain over.** `POST /` and `PUT /:id` answer 409 `IDENTIFIER_EXISTS`, naming the domain and its config, when a zone the change adds covers a domain assigned to another config more specifically than that config's own zones do (a domain whose config no longer covers it at all is manual already and ignored). The admin sets the domain to manual, adds the zone, and assigns the domain to the config (10.4).
- **A zone belongs to one config.** `POST /` and `PUT /:id` answer 409 `IDENTIFIER_EXISTS`, naming the zone and the config, when a zone is already in another config (compared after normalization, enabled or not); on an update only the zones the change adds are checked, so a row that already shares one from before can still be edited otherwise. Nested zones (`mail.example.com` under `example.com`) are different zones. There is no unique index over the elements of a list, so two creates racing for one zone can both pass the check; the controller then refuses the desired state whole (7.4) and the console shows it.
- `DNS_PROVIDER_DELETE` records `name` and `type`; the credentials go with the row.

### 10.2 `system/integrations`

`GET` returns each section's effective values, `defaults` (from config on every request, as in 2.4), `source` per field (`"admin"` or `"deployment"`), and secrets as masks. `PUT /:section` updates one section; `POST /:section/reset` (body: optional keys, all when omitted) deletes the admin values so the deployment default applies.

As implemented (restapi step 5, `BaseIntegrationsRoute`, `src/util/IntegrationSettingsUtils.ts`):

- **Response** (`GET` and both writes): `{ <section>: { values, defaults, source }, version }`. `values` and `defaults` show a secret as the mask when set, else `null`; `stun.urls` is `null` while neither the administrator nor config sets it, or config sets an empty list (the meet plugin's built-in list); URLs from config are shown without any user name or password they carry (`withoutUrlCredentials()`: a deployment may put registry credentials in the URL, which `NpmRegistryClient` sends as Basic auth); `version` is the row's (0 before anything was saved). While the administrator's registry `url` is another registry than the deployment's (`sameRegistryUrl()`: the parsed URLs, credentials aside), the view shows what the layer does: `token` is `null` with `source: "admin"` unless the administrator set one, and the deployment's namespaces (when the administrator set none) lose the token mask of those on the default registry.
- **`PUT /:section`**: a field left out is unchanged, `null` puts it back to the deployment's value (and removes its secret), a secret sent back as the mask is kept. A namespace's `token` follows the same rule inside the list, which replaces the saved one: a namespace taken off the list loses its token. An unknown field is a 400 that lists the section's fields and never repeats what was sent. Optional `version`: a change made against another one is a 409 (`INVALID_OBJECT_VERSION`) before anything is written. A request that changes nothing writes and audits nothing.
- **`POST /:section/reset`**: body `{ keys?, version? }`; `keys` must be fields of the section.
- **Order of writes:** the request is validated first (URL lookups included), then the row is read and its version checked, then new secret values are encrypted (5.2) and the row is written once. A write that lands meanwhile is merged field by field (the row write is retried on the newer row, at most 3 times; the write saved last wins a field both set, a clear included). The plugin namespaces and their tokens are one unit, the tokens now stored inside the namespaces (4.5): a change to the namespaces whose tokens another write changed meanwhile is a 409, never one request's list saved with the other's tokens. (As first built, secrets went to a store path per write before the row, with cleanup of replaced, failed and left-behind secrets and a 400 without a store; the rework deletes all of that, 18.)
- **`defaults`** come from the route's `@Config` values (`deploymentConfig()`), with the server's built-in defaults where config sets none (`DEFAULT_RFC8823_DIRECTORY_URL`, `DEFAULT_DOH_ENDPOINT`, `DEFAULT_PLUGIN_REGISTRY`, `DEFAULT_PLUGIN_NAMESPACES`, the signing backend `manual` and the resolver `node`). They must not include the server's integrations layer (11.1): the server builds the route before installing the layer, or overrides `deploymentConfig()`.
- **Change notice:** after every saved change the route calls `integrationsChanged(settings)`, which does nothing in restapi; the server overrides it to publish `rapidmx:integrations:changed` (11.2). A failure there is logged, never the request's.
- **The layer:** `buildIntegrationsConfigLayer(settings, cipher, deployment)` turns the row into the flat config keys the administrator set, with the secrets decrypted (5.4; a secret that can't be decrypted is left out and reported, so the deployment's value applies; first built with a `SecretStore` argument); Giphy turned off also sets `giphy:api_key` to `""`. **The deployment's registry credentials stay with the deployment's registry:** `deployment` is the server's configuration without the layer (the same flat keys `integrationDefaults()` reads), and while the administrator's registry `url` is another registry than its own, the layer sets `system:plugins:registry_token` to the administrator's token or `""` (none: also when the administrator's can't be read), and, unless the administrator set the namespaces, the deployment's namespaces without the tokens of those on the default registry (a namespace on its own registry keeps its token, which never goes to the default one). Otherwise a private registry's token would go, as `Authorization: Bearer`, to whatever host the administrator's URL names (an independent review's finding). The server's layer (server step 6) is built with it, so the route's defaults and the layer can't name different keys (`INTEGRATION_CONFIG_KEYS`).
- **As implemented (restapi R3).**
  - **The layer function** is synchronous (the cipher decrypts synchronously, 5.2) and answers `{ values, unreadable }`: `unreadable` lists the row fields it couldn't decrypt (`giphy.apiKey`, `pluginRegistry.token`, `pluginRegistry.namespaces.<scope>.token`; a missing key, an envelope from another field, a value that isn't an envelope), for the server's warning once per field (5.4), never why or what. A namespace whose token can't be read stays on the list without it. Giphy turned off decrypts nothing. Any failure other than `ConfigSecretUnavailableError` is a bug and is thrown. (First built as the async `buildIntegrationsConfigLayer(settings, store, deployment)` answering `{ values, unresolved }` with config keys.)
  - **Associated data** is built by `integrationSecretContext(field)` from `INTEGRATION_SETTINGS_RECORD`, `INTEGRATION_SETTINGS_UID` and `GIPHY_API_KEY_FIELD`, `PLUGIN_REGISTRY_TOKEN_FIELD` or `pluginNamespaceTokenField(scope)`; `pluginNamespaceTokenKey()`, the secret store's key for a namespace, is gone.
  - **The route** injects `"ConfigCipher"`. A secret is sealed when the change is worked out against the row just read, after the version check and only for a request that changes something, so a server without a cipher answers 503 (`noConfigCipher()`, now taking the name of what can't be handled) or without a keyring (`ConfigCipher.encrypt()`'s own 503) before anything is written; clearing a secret, keeping one sent back as the mask and saving namespaces without tokens need no cipher. A secret sent again always counts as a change (a saved one can't be compared with it without decrypting). It is sealed once, so a retry on the newer row saves the same envelope. A namespace sent without `token` (or with `null`) is saved without one; only the mask keeps the saved token of the same scope.
  - **The 409 for the namespaces** compares the tokens (by scope, as the text of each envelope) of the row the request saw with those of the row it is applied to; a list change alone, with every token unchanged, is merged (the list saved last wins). A re-encryption by the key rotation that lands in between changes the envelopes and so is a 409 too, which the console answers by reloading (the same as any other change, since it moves the row's version).
  - **A clear is not guarded.** First built, a clear removed a secret only while the row still named the reference it had seen, so the other write's new secret in the store wasn't deleted; with the secret in the row there is nothing to delete, and a clear is a write to the field like any other (the write saved last wins).
  - **Re-encryption:** `integrationSettingsEnvelopeSource()` (`src/util/IntegrationSettingsEnvelopeSource.ts`, registered by `ConfigKeyRotationJobMongo`/`SQL`) lists the three kinds of field under their paths and saves the whole `giphy` and/or `pluginRegistry` section that holds a replaced envelope, and nothing else.
  - **Unreadable secrets in the view (not R3).** `GET system/integrations` shows the mask for any envelope on the row and never decrypts, since a request must not decrypt (decrypted secrets are cached in memory for the process lifetime, not read per request). "Set, but can't be read: enter it again" (5.4) therefore comes from the server, which passes the layer's `unreadable` to Diagnostics (server step) and the console (W1), the same as for DNS provider credentials. A PUT that sends the mask back keeps an unreadable envelope; entering the value again replaces it. **The wire shape (web-client W1, decided with the console):** the server marks such a secret by adding `unreadable: true` to its mask, `{ "secret": true, "unreadable": true }`, on every secret the console shows (a DNS provider's `credentials.<field>`, `giphy.apiKey`, `pluginRegistry.token`, a namespace's `token`); the console shows the field as "Set, but can't be read: enter it again" and still sends the plain mask back for it (never the flag). restapi's own views never set it, since they never decrypt: the server's route subclasses add it from what the process has already tried to decrypt (the layer's `unreadable`, the credentials endpoint's, the re-encryption pass's), never by decrypting for the request (S2 for the DNS provider route, S6 for integrations).
  - **Open follow-up for the rotation job (all envelope writers, R2 and R3 alike).** A route seals with the cipher's active key, then saves the row some round trips later (more on a retry). `stepRetiring` removes a key as soon as a complete pass counts no envelope on it, with no grace period, so a write sealed under the old key before this copy's heartbeat reported the new one, and saved after the pass and the retirement, leaves an envelope that no replica can read. The window is the length of one save. Fix in the job, not the routes: retire only after a second complete pass, or recount right before the keyring write.

### 10.3 Validation of URLs

Every URL field is parsed, must be `https:` (except STUN URIs), must have a host, and the host must not resolve to a private, loopback or link-local address at save time.

As implemented (`normalizeIntegrationUrl()`): at most 2048 characters without control characters; no user name or password (a credential in a URL would be saved in the database); the host is judged as the URL parser reads it (a number-encoded IPv4 address as the address it is), an IP literal directly and a name by its addresses, against the ranges key discovery refuses (`isPublicDiscoveryAddress()`: this host, private, shared and link-local networks, multicast, unique-local IPv6, and IPv4-mapped forms of them). A name that doesn't resolve, or not within 3 seconds, passes: nothing can be connected to through it either. The error names the field and never repeats the URL. STUN URIs (`normalizeStunUrls()`, 1 to 10 of them) are `stun:`/`stuns:` with a host name, IPv4 or bracketed IPv6 address and an optional port from 1 to 65535, nothing else, lowercased and each once; they are handed to browsers, never fetched by the server, so a private host is allowed. `contactEmail` is one plain address of at most 254 characters.

### 10.4 Assigning a domain

`PUT mail/domains/:id/dns-provider` with `{ dnsProviderUid: string | null }`: trusted role and elevation, checks the provider exists and its zones cover the domain (400 otherwise), audits `DOMAIN_DNS_PROVIDER_ASSIGN`, bumps the desired-state version (from restapi step 3, when `DnsPublisher` exists). Assigning the provider the domain already has changes nothing. **As implemented (restapi R2), only the most specific config covering the domain is accepted** (400, naming the config that covers it better and its zones): another config whose longest zone covering the name is longer wins, enabled or not, since its external-dns instance leaves its zone out of the parent's (7.4). **Adding a nested zone is refused while a domain is assigned to another config that the new zone covers more specifically** (409, on `POST /` and on a `PUT /:id` that adds zones, naming the domain and its config, 10.1): the nested instance would take the domain's records for its own and delete them (7.4), so the admin sets the domain to manual first, adds the config, then assigns the domain to it. Seeding (13) follows the same rule: a seeded domain another config covers more specifically is created manual, with a warning. A provider deleted, or its zones narrowed, at the same moment as an assignment can leave a domain assigned to a provider that no longer covers it; that is harmless (external-dns publishes only inside its `--domain-filter`), and the desired state (step 3) treats such an assignment as manual (`no_provider` or `outside_zones`).

### 10.5 `system/config-keys`

The configuration keyring's console (5.5), restapi `BaseConfigKeyRoute`:

| Route | Behaviour |

| `GET /` | Trusted role. The ring's `kid`s with their age (`createdAt`) and envelope counts, which one is active, and the current or last rotation from `ConfigKeyState` (4.9): its phase, whether it is compromised, the copies still loading the new key (`waitingFor`) with the warning once `config_encryption:activation:warn_minutes` has passed, whether it was activated anyway (`activationForced`), the re-encryption's progress and `lastError`. ## 11. Live Application

Today nothing is live (2.6). Reusing the plugin rolling restart (adding the `IntegrationSettings` version to the state hash) would restart every replica for a Giphy key change, so it is only a fallback for a consumer that cannot be made live in the first release.

### 11.1 The integrations config layer and `HostConfig`

- The server adds an nconf layer `integrations` directly below `plugins`; `integrations` is added to `CORE_CONFIG_NAMESPACES` (done in restapi step 5; every other key the layer sets was already under a protected namespace), so a plugin can never declare or save these keys. On start and on every change notice the server rebuilds the layer from the `IntegrationSettings` row, decrypting its secrets (5.4): the layer is where the plaintext is kept for the life of the process.
- restapi gains a static, read-only accessor `HostConfig.get(key)`, which the server installs at startup over its live nconf instance (`HostConfig.install(config)`). Before installation it returns `undefined` (`HostConfig.isInstalled()` says which). Plugins share the class with the server (restapi is their peer dependency), so nothing can write the server's configuration through it or redirect what it reads: it has no setter; an object or array value is returned as a deep copy; a configuration is installed **once** (the server does it before loading any plugin, and a later `install()` throws); `install()` returns the only handle that uninstalls it (for tests and shutdown); the installed source is module-private; and the class is frozen, so `get` can't be replaced. It is how code that was built with `@Config` (a startup snapshot) reads a value at use time, plugins included, without reaching into `ObjectFactory`'s protected `config`.

### 11.2 Propagation

A write publishes `rapidmx:integrations:changed` (row version) on Redis; every replica rebuilds the layer and notifies the consumers below. A replica that misses a message catches up within a minute (it compares the row version on a timer).

## 12. Installer (server)

### 12.1 Flags

- `--dns-provider <type>` (env `DNS_PROVIDER`): turns publishing on, installs the CRD, and creates the first provider config with `zones` = the zone of `--domain` (or `--dns-zone <zone>` when the domain is below the zone apex). For Cloudflare the installer looks up the zone id with the token.
- Credentials: `--dns-credentials-file <path>` (a `KEY=value` file, read once) or the provider's own environment variables (`CF_API_TOKEN`, `AWS_ACCESS_KEY_ID` ...), never a command-line value. The installer passes the non-secret part to the chart (`mail:dns:bootstrap_provider`, JSON: `{ name, type, zones, options }`) and the credentials in a Kubernetes Secret, `<fullname>-dns-bootstrap`, which only the server pod mounts (`optional: true`); the server turns them into the `DnsProvider` row once (`origin: "installer"`, credentials encrypted, 5.2) at startup, idempotently, before it reports ready, and the installer deletes the Secret once the rollout is ready, so the database is the only place the credentials stay (decided by JP, 2026-10-28; first designed as a reference to credentials the installer wrote to OpenBao or to the provider's Secret).
- `--dns-takeover`: sets `allowTakeover` on that config.
- `--public-address <ip>` (repeatable): overrides address detection (6.4).
- `--keep-dns` for `--uninstall` (9.5).

### 12.2 OpenBao

`prepareOpenbao` additionally: enables the `kubernetes` auth method (pointing at the in-cluster API, using OpenBao's own ServiceAccount for token review, which the OpenBao chart already grants); creates the roles and policies of 5.8 (the server's with read and write on the keyring path only, External Secrets' with read on it; the rework removes the `<fullname>-dns-controller` role and the `integrations/*` paths that server step 2 created, 18); creates the configuration keyring at `<kv>/<fullname>/config-keyring` when it doesn't exist, copying the existing `<fullname>-config-keyring` Secret's keyring when the deployment had one (5.3); issues the listener certificate and switches the listener to TLS (5.8), restarting and unsealing through the existing `openbao-unsealer`; copies the CA into the release namespace; migrates the ESO and PKI tokens and revokes them. On an upgrade of an existing installation it does the same idempotently.

Renewal (**decided by JP: a reload sidecar, no restarts**): cert-manager renews the leaf certificate (1 year, renewed 30 days before expiry), and OpenBao re-reads its listener certificate on `SIGHUP`. The installer adds a small sidecar to the OpenBao pod (`shareProcessNamespace: true`), running the already-pinned OpenBao image (so no new image) with a short shell loop: every 30 s it hashes the mounted `tls.crt` and `tls.key` (the kubelet swaps the Secret volume's `..data` link when cert-manager writes the renewed Secret) and, when the hash changes, sends `SIGHUP` to the `bao server` process. It runs as OpenBao's own uid (signalling needs no capability), read-only root filesystem, all capabilities dropped. A sealed or restarted OpenBao is never involved: `SIGHUP` reloads the listener without sealing. The installer's check after an upgrade verifies the served certificate's expiry matches the Secret's. As implemented: the sidecar (`tls-reload`) skips a round while either file is empty, signals only a process whose first two arguments, read as separate arguments, are `bao` (or a path ending in `/bao`) and `server` (the sidecar's own `sh -c` holds the script, "bao server" included, in its command line), never itself, ignores `SIGHUP`, and retries a change that found none; it runs as uid 100/gid 1000. An existing plain-HTTP vault is moved to TLS by deleting its pod when it runs an older revision than its StatefulSet (the chart's `OnDelete` strategy); it comes back sealed and is unsealed by the installer or the unsealer, which now reaches the vault over TLS with only the `ca.crt` of `openbao-tls` mounted. The certificate check port-forwards to the pod and compares `openssl x509 -enddate` of both, reporting a difference without failing (skipped without `openssl`).

### 12.3 Final message

With a provider: the records being published, the hosts and records that stay manual (and why), and how to watch progress. Without: the records to add per host and per domain. Always: that the configuration keyring (the Secret `<fullname>-config-keyring`, or the OpenBao KV path) must be backed up with the database, which is useless without it (5.9).

### 12.4 Uninstall

As in 9.5, then the existing uninstall steps; the CRD is removed only when the installer installed it and no other release uses it. The keyring Secret is kept (5.3) and the installer says so, since a kept database needs it; removing it is a separate, explicit step.

### 12.5 The openpgpkey host

- **A provider manages the install domain**: the chart default for `mail.wkd.openpgpkeyHost.enabled` becomes on, with a **two-step HTTP-01 install**: the first `helm upgrade --install` runs without the openpgpkey host; the installer waits (bounded) until `openpgpkey.<domain>` resolves to the server; the second `helm upgrade` turns the host on, so the Certificate's HTTP-01 challenge can succeed and Helm's `--wait` does not block.
- **No provider**: the installer enables the host when `openpgpkey.<domain>` already resolves to the server, else leaves it off and prints the record to add (`--openpgpkey-host` still forces it on).
- **Admin console**: the domain's DNS panel warns when `openpgpkey.<domain>` does not resolve to this deployment.

## 13. Domain Seeding

### 13.1 Config: `mail:domains`

`mail:domains` (2.8) becomes the list of domains the deployment is installed for. Each entry is a string (the domain name) or an object:

```ts
interface SeedDomainEntry {
    name: string;
    /** The DnsProvider to assign: its `uid`, or "bootstrap" for the installer's provider config (the one `DnsProvider` with `origin: "installer"`). */
    dnsProvider?: string;
    dmarcPolicy?: "none" | "quarantine" | "reject";
    dmarcReportEmail?: string;
    /** Another seeded or existing domain this one aliases. */
    aliasOf?: string;
}
```

- A comma-separated string is accepted too (as `normalizePluginNamespaces()` accepts one), so `mail__domains=a.com,b.com` works. As implemented (restapi step 6, `parseSeedDomainEntries()`), so are the list as JSON text (a ConfigMap value nconf left unparsed) and one object on its own; names are trimmed and lowercased, and an empty name in a comma-separated string (`a.com,,b.com`) is nothing rather than a mistake.
- The chart renders the values list `mail.domains` into the service ConfigMap as JSON (`mail__domains: {{ $list | toJson | quote }}`), the same way `cors__origins` is passed. When the list is empty it defaults to `global.domain` plus each name in `postfixBridge.domains` (de-duplicated), each with `dnsProvider: "bootstrap"` when publishing is enabled. The installer's `--mail-domains` feeds it with no new flag.
- `mail:domains` is already on both protected lists. The stale doc comments (2.8) are corrected, and the `yarn dev` helper's `["example.com"]` now seeds a real `example.com` domain, which is what local development wants.

### 13.2 Validation

Each entry is validated on its own with the same rules as `BaseDomainRoute.create()`. An invalid entry is **logged as a warning and skipped**; an unknown provider, or one whose zones do not cover the name, is logged and the domain is created without a provider. Nothing here stops the server. Duplicates: the first entry wins.

As implemented (restapi step 6): the rules are literally the console's, since `BaseDomainRoute.create()` and the seeder share one create path, `prepareNewDomain()` in `util/DomainUtils.ts` (host-name check, DMARC policy, alias checks, verification token, DKIM key, reserved-TLD carve-out, 409 on an existing name). `parseSeedDomainEntries()` checks only each entry's shape first: an entry that isn't a name or an object with one, an option that isn't text, and an **unknown option key** (a misspelled `dnsprovider`) skip the entry, naming the key, rather than seeding the domain without the option, since a seeded domain is never changed again from the configuration. A skipped entry isn't recorded as seeded, so the corrected entry is seeded on a later start. `"bootstrap"` with no installer provider, or more than one, is logged and the domain created manual.

### 13.3 Behaviour

At startup, after migrations, `DomainSeeder` (restapi `src/util/DomainSeedUtils.ts`, with `DomainSeederMongo`/`DomainSeederSQL` in `src/util/{mongo,sql}/`, run by the server: `await seeder.run()`, which never throws and returns what it created, recorded, skipped and adopted):

- **Creates a domain only when it is absent and was never seeded before.** The names seeded so far are recorded in `SetupState.seededDomains: string[]`, append-only. A name on that list is never created again, so a domain the admin deleted stays deleted even when the config still lists it, and even after a `purge` delete.
- **Never overwrites an existing domain**: the admin's edits win. An existing hand-made domain is recorded as seeded without change.
- **A name removed from the list is not deleted.**
- Creates through the same code path as `create()` (verification token, DKIM key, audit entry `DOMAIN_CREATE` with `details.origin: "seed"` and no user), with `origin: "seed"`, and assigns the provider directly. As implemented, the audit entry also carries `dnsProviderUid` when one was assigned, and each created domain is announced to the `DnsPublisher`.
- **Multi-replica safety**: the create is keyed by `uid` = name, so a concurrent create by another replica fails with a collision, treated as "already there"; the `seededDomains` append uses the setup row's optimistic version with `BaseSetupRoute`'s retry. No lock is needed. As implemented, that retry is `updateSetupState()` (`util/SetupStateUtils.ts`), which `BaseSetupRoute`'s step save, `complete()` and `reopen()` now use too; each attempt appends to the row as re-read, so a name another replica recorded meanwhile is kept.
- As implemented: a name is recorded right after its domain is created or found, never before (a failed create is retried on the next start); an alias entry is created after the others, so it may alias a domain listed after it; nothing is written to the setup row unless there is a name to record; when the seeded names can't be read, nothing is seeded on that start (a deleted domain could otherwise come back), and when a name can't be recorded, the next start records the existing domain. `seededDomains` is read again right before each create (after the entry's key is generated), so a domain another replica seeded and the admin deleted while this replica was still busy with earlier entries isn't created again.
- **Upgrades are adopted, not seeded** (decided in restapi step 6 review): "never re-created after deletion" can only hold for deletions the seeder saw. On a deployment that predates seeding, a listed name may be a domain the admin deleted back then, or one never added on purpose (the chart default lists `global.domain`, often only the hosts' base domain), and creating it would mint a DKIM key and, with the bootstrap provider, publish its records. So while `seededDomains` is empty and a domain from before `Domain.origin` exists (counted as all domains minus `origin: "seed"` minus `origin: "console"`; total read first, so a concurrent seed create can only hide, never fake, an old row), the seeder records every listed name as seeded without creating any (`adopted` in the result, with a warning telling the admin to add any missing one in the console). Names added to the list afterwards are seeded normally. A fresh install never has such rows (every domain it gets has an origin), and a deployment from before seeding with no domains left is seeded like a fresh one. When the domains can't be counted, nothing is seeded that start; when the adoption can't be recorded, the next start adopts again. Not keyed on a completed setup: on a fresh install an admin can finish setup before a corrected entry is seeded, and that entry must still be created.

### 13.4 Verification

With a provider, the ownership TXT is published with the other records, so `DomainVerificationJob` verifies the domain within minutes. Without one, it stays unverified until the admin publishes the TXT record. A reserved-TLD domain starts verified, as today.

### 13.5 Setup wizard

- `BaseSetupRoute.toStatus()`: "no domains" becomes "no domains other than seeded ones" (`origin !== "seed"`), so a fresh install with seeded domains still gets the wizard, and an existing deployment is never pulled into it. As implemented, it compares the count of all domains with the count of `origin: "seed"` ones (required when the seeded count is at least the total, so a domain seeded between the two reads doesn't flip it), since an `origin != 'seed'` filter on SQL would leave out the rows without an origin.
- The wizard's `domain` step lists the seeded domains as already added ("Added from your installation"), each with its DNS panel. Adding more stays available, and the step no longer blocks when a seeded domain exists.
- The installer's final message says the domains are already in the admin console.

## 15. Security Considerations

- **Kubernetes rights are isolated.** The internet-facing server keeps read-only Kubernetes access to every resource but one: without OpenBao, the configuration keyring Secret it rotates (below, 5.5). The controller holds the write rights, but runs its own minimal image (no server code, no runtime dependencies, distroless, non-root, read-only root filesystem), has no database or Redis access, serves no API (only its health endpoints; every call goes from it to the server), and runs only the pinned external-dns image.
- **Configuration secrets at rest** (§5). Every credential, API key and token in the database is AES-256-GCM encrypted with the deployment's keyring and bound to its record and field, so a database dump or backup alone reveals none, and an envelope moved to another field doesn't decrypt. The keyring reaches only the server pods; the controller and external-dns never see it. The threat addressed is a leaked database or backup; **a compromised server process is not**: it holds the keyring and the decrypted values in memory (decided by JP, 5.4: decrypting per use would not stop that attacker and costs performance). Rotation is manual (an elevated, audited admin action, also for a suspected compromise of the keyring), performed by the server: it adds the new key, activates it once every server copy has loaded it, re-encrypts every value and then removes the old key (5.5).
- **Credential exposure.** DNS credentials can redirect a domain's mail and obtain certificates for it. They are stored encrypted on their `DnsProvider` row, decrypted by the server only to answer the controller's credentials request, and written by the controller into the one Secret their external-dns pod reads; they are absent from logs, audit entries, Diagnostics and Deployment specs. They cross the cluster network from server to controller on each credentials change, over the server's internal API in plain HTTP, as the existing internal mail traffic does (**decided by JP, 2026-10-28**, 7.3): the route is never reachable through the Gateway and answers only the controller's token, and TLS on that hop would guard only against someone observing pod-to-pod traffic, who already has node-level access and with it the keyring and the database, so it would address no real threat. Recommend scoped tokens; for Cloudflare: Zone:Zone:Read and Zone:DNS:Edit on the one zone, with its zone id in the config.
- **The server's one write right** (approved by JP, 2026-10-28) is the keyring: without OpenBao `get` and `update` on the one Secret `<fullname>-config-keyring` by `resourceNames`, with OpenBao read and write on the one KV path `<fullname>/config-keyring` and no Kubernetes write right at all. **It stays read-only on every other Kubernetes resource.** This adds no exposure of the keys: the server already holds the keyring through its mount. What it adds is that a compromised server could replace or empty the keyring (a denial of service, the values encrypted with a lost key becoming unreadable, recoverable from the keyring's backup, 5.9); a compromised server could already damage the database it writes. Moving rotation into the server removed a CronJob, an image and an internal API that would each have needed hardening.
- **OpenBao** is reached over TLS with a pinned CA, and every client logs in with a short-lived, audience-bound ServiceAccount token to a policy scoped to its own paths. No long-lived tokens remain. OpenBao is optional: without it the keyring is a Kubernetes Secret, as readable as the release's other Secrets to whoever can read Secrets in the namespace.
- **Who can publish.** Creating providers, changing credentials, assigning a domain, taking over records, rotating DKIM and changing integrations all need a trusted role and an elevated token, and are audited. Adding a domain (trusted role, as today) can now create public DNS records automatically, but only inside zones an elevated admin attached to a provider config.
- **Zone confinement.** A provider config can only touch its zones: `--domain-filter`, the zone check on assignment and seeding, and the credentials' own scope. The TXT registry and the per-deployment owner id keep each deployment to its own records in a shared zone.
- **Ownership verification.** When RapidMX publishes its own verification TXT, verification proves that this deployment holds credentials able to edit the zone, which is at least as strong as pasting the record by hand. It no longer proves that a separate human acted; that is acceptable because attaching the provider already required an elevated admin. Verification is still only by public DNS lookup. The record lives at `_rapidmx-verify.<domain>` (6.5), so verifying never puts the apex TXT set under RapidMX's control.
- **Takeover** can overwrite records other systems depend on, and a taken-over set is owned whole (9.3): opt-in per provider, per-domain confirmation, the apex TXT set only on its own opt-in with an explicit, editable list of values to keep (9.4), kept values restored on opt-out, deletion and uninstall (9.5), and the old values in the audit entry.
- **Version skew.** The controller and the server refuse to act on an API version they do not both speak (7.3), so a mismatched pair cannot misread desired state into wrong records.
- **DKIM rotation** never switches signing to a key whose record is not live, so a rotation cannot break DKIM; a compromised key is retired as soon as signing has switched.
- **SSRF.** URL fields are validated as in 10.3.

## 16. Failure Modes

| Failure | Behaviour |
| --- | --- |
| CRD not installed | Publishing reported unavailable; domains behave as manual. |
| Controller down | Desired state keeps accumulating; nothing is published or removed until it is back; the console shows the controller as down. |
| Controller and server API versions incompatible | The controller refuses to act (no Lease, no writes), reports not ready, retries the handshake every 60 s; the server records the mismatch and the console shows both versions. |
| Lease lost (API server unreachable, pod paused) | The controller stops writing at once and re-acquires before writing again. |
| Restoring kept apex values fails | Shown in the console with the values to re-add by hand; logged. |
| Controller cannot fetch a provider's credentials (server down, a field that can't be decrypted) | The provider's Secret stays as it is and its pod keeps running; the controller retries with backoff and the provider shows the error. |
| Bad credentials / provider API down | external-dns retries; the provider shows Error with the last error; records keep their last state. |
| Record conflict | `conflict` with the existing value; nothing overwritten unless takeover. |
| Provider cannot hold a kind | That record is manual with its reason; the others publish. |
| No keyring in production (Secret missing, malformed, empty) | The server refuses to start, saying so; running pods keep the keyring they loaded. |
| A value's `kid` not in the keyring (a restore with an older keyring) | That value is left out (deployment value or plugin default applies), logged once per field, shown "can't be read: enter it again"; re-encryption leaves it and the server never removes a `kid` it still counts. |
| A rotation's keyring write is refused (version conflict, OpenBao sealed, a missing right) | The ring is unchanged; the step is retried on the next run; the console shows `lastError`. |
| A server copy never loads the new key (a stale kubelet mount, External Secrets not syncing) | Activation waits and the old key keeps encrypting; the console names the copies and, after `config_encryption:activation:warn_minutes`, warns that restarting them resolves it. Nothing breaks meanwhile, and it never activates on its own. An admin who knows the copy is being replaced may "Activate anyway" (elevated, audited); that copy then can't read values saved with the new key until it is replaced, and re-encryption waits for it to go. |
| Old server pods still running when the plugin secret settings would be encrypted (a rolling upgrade), or the pods can't be listed | The encryption run waits, secret settings stay in plaintext as before (saves too), and Diagnostics and the console say why; it runs once no pod of an older ReplicaSet is left. |
| Redis unavailable during a rotation | No heartbeats, so activation waits (it never activates on missing reports); the old key keeps encrypting. |
| Re-encryption interrupted (a replica restarts, a row changes meanwhile) | The next run continues; old keys stay until a full pass finds none of their envelopes. |
| Keyring Secret replaced by hand or by a bad keyring write | Values encrypted with a lost key show as unreadable (above); restore the keyring from its backup (5.9). |
| OpenBao sealed or unreachable | External Secrets keeps the last synced keyring Secret, so servers start and decrypt; a rotation waits at its next keyring write (the server can't write the KV path); the PKI CA fails as before. |
| New DKIM record never goes live | Rotation stays `pending`, signing unchanged; the console reminds the admin. |
| postfix-bridge does not acknowledge a switch | Both selectors stay published; no overlap clock; `lastError` shown; the admin may cancel, which reverts signing to the old key. |
| Two deployments share a zone | Separate owner ids; a name both want is a conflict for the second. |
| An external-dns Deployment removed by hand | The next reconcile re-creates it. |
| Public addresses empty or private | Hosts not published; the console says why. |

From JP, 2026-10-28 (amendment: configuration-key rotation):

- **Configuration-key rotation is manual only and performed inside the server** (5.5). From JP, 2026-10-28 (approval of the spec, its open questions and the DNS checks):

- **Keyring reload** (5.3): the keyring file is re-read every minute, at once on the rotation notice, and on an envelope naming an unknown `kid` (at most once a minute).
- **Activation once every copy has the key** (5.3, 5.5): a new key encrypts only once every live server copy reports it through its Redis heartbeat (every 30 s, TTL 90 s); meanwhile the current key keeps encrypting, so nothing breaks; a dead copy drops out when its heartbeat expires; after `warn_minutes` (15) the console names the stale copies. It never activates on a timeout. An elevated, audited **"Activate anyway"** (`POST system/config-keys/activate`) is for an admin who knows a stale copy is being replaced.
- **The keyring Secret** (5.3) is rendered only when `lookup` finds none, with `helm.sh/resource-policy: keep`, and owned by the server's rotation afterwards.
- **The plugin-state hash** (5.7) counts a secret setting by its decrypted value.
- **Rolling upgrade with encrypted plugin settings** (5.7): no release-note requirement. The encrypt-in-place run waits until every pod of the server Deployment runs the new release, checked through the server's existing read-only Kubernetes access, then runs; on powerlevel.gg (one replica, `Recreate`, no stored secret plugin setting) it is an immediate no-op. This replaces the first proposal, a release note requiring the rollout to finish.
- **`v1` changed in place** (7.3): `DnsProviderV1.secretRef` becomes `credentials` without a version bump, since neither side has released `v1`.
- **Installer bootstrap credentials** (12.1) reach the database through the server-only temporary Secret `<fullname>-dns-bootstrap`, deleted once the rollout is ready.
- **`IntegrationSettings` field names** (4.5): `apiKeyRef`/`tokenRef` become `apiKey`/`token`, and each namespace carries its own `token` (`namespaceTokensRef` dropped).
- **The spec's additions, approved as listed:** `config_encryption:keyring_store:*` (`kubernetes`, `openbao`, `file` or `none`, `none` answering rotation with 503); the activation heartbeat of 30 s and the warning after 15 minutes; `ConfigKeyRotationJob` every 30 s while it has work, plus the Redis notice; the chart values `configEncryption.externalSecretRefreshInterval` (1m) and `configEncryption.rbac.create`; one rotation at a time (409, `compromised: true` upgrading a running normal one).
- **Route 53 TXT quoting settled** from external-dns v0.23.0's source (4.2): Route 53 sends and reads TXT values verbatim, so quoted targets are a no-op sync; values are compared without regard to case. **Values over 255 bytes must be pre-split** into quoted chunks: Cloudflare splits an unsplit value itself and then re-plans it on every sync (confirmed live).
- **An unowned record at a name blocks only creation there** (9.3, confirmed live on powerlevel.gg): updating and deleting an owned MX next to an unowned apex TXT set work through the regular instance, so the one-shot Job is needed only for the MX's first creation.
